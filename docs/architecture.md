# Optiply Workflows: a Retool-style internal platform

## Context
Optiply wants its own internal-tools platform, built like Retool but with our own interface. It will let us connect data sources (**Resources**), automate backend processes (**Workflows**), keep simple tables (**Database**), and later build internal UIs (**Apps**).

The repo (`/Users/optiply/optiply-workflows`) is empty, so this is a greenfield build.

Decisions so far:
- **Stack:** TypeScript full-stack (React + Vite, Node, Postgres).
- **Audience:** a single org, self-hosted, for Optiply internal use only.
- **MVP focus:** Resources and Workflows first. Database and the App builder come in later phases.

Part 1 explains how Retool works. Part 2 is the build plan.

# Part 1: How Retool works

> Retool runs two app builders as of 2026. In **classic apps** you drag and drop components and wire them up with `{{ }}` bindings. The **new app builder** (beta since May 2026) has an AI agent that generates React 19, shadcn and Tailwind code, with server-side TypeScript functions. Everything below describes the classic model, which is the core of the product and what we are cloning.

## 1.1 Platform architecture
- **One backend image, many roles**, chosen with `SERVICE_TYPE`:
  - `api`: serves the frontend and REST API, and runs queries from apps.
  - `db-connector` / `db-ssh-connector`: execute queries against resources.
  - `jobs-runner`: exactly one replica. Runs migrations, Git sync and cron jobs.
  - `multiplayer`: WebSocket co-editing.
  - `workflows-worker`: a Temporal worker.
  - `workflows-backend`: runs queries for workflows and stores block results.
  - `code-executor`: user JS and Python, sandboxed with nsjail.
  - `agent-*`.
- **Dependencies:**
  - **Postgres**: the platform database holding apps, resources (encrypted), users, permissions, `page_saves` history, `audit_trail_events`, `workflow_run` and `workflow_block_results`.
  - **Temporal**: durable execution for Workflows and Agents.
  - Optional Redis (cache) and S3 (large block results).
- **Secrets:**
  - `ENCRYPTION_KEY` (AES-GCM) encrypts resource credentials. Losing it means losing every resource.
  - `JWT_SECRET` signs sessions.
- **Queries always run on the server.** The browser sends the query ID plus the evaluated `{{ }}` values. The server loads the resource config, decrypts the credentials, and executes. Credentials never reach the browser.
  - SQL `{{ }}` values become **prepared-statement bind parameters**, which prevents SQL injection but means you cannot pass a dynamic table name.
  - `current_user` is injected on the server, which prevents spoofing.
- **Tech stack:** TypeScript, Node and React (18), built with Vite. App state is probably Redux plus Immutable.js. User JS runs in a **cross-origin iframe**, on a separate `SANDBOX_DOMAIN`.

## 1.2 Resources (connections)
- There are about 80 connector types:
  - **SQL:** Postgres, MySQL, MSSQL, Snowflake, BigQuery, …
  - **NoSQL:** Mongo, Redis, Dynamo, …
  - **APIs:** REST (manual or from an **OpenAPI spec**), GraphQL, gRPC.
  - **SaaS:** Stripe, Slack, Google, Salesforce, …
  - **AI:** OpenAI, Anthropic, …
  - **Storage and messaging:** S3, SQS, Kafka.
- **Config per environment:** each resource has separate host and credentials for `production` and `staging`, plus any custom environments. Apps and workflows stay the same; only the resource binding changes, selected with `_environment` or `?environment=`.
- **Auth methods:**
  - API key, Basic, Bearer, AWS SigV4, Google service account.
  - **OAuth2**: authorization code, client credentials or PKCE, with tokens stored per user and per environment, or shared via "share credentials between users".
  - **Custom auth flows**: ordered steps (form → API request → JS → define variable) plus a refresh flow that retries once after a non-2xx response.
- **Networking:** SSH tunnels through a bastion host, SSL client certs, and an outbound IP allowlist.
- **SQL query editor:**
  - **SQL mode**: raw SQL with bind params.
  - **GUI mode** for writes: insert, update, upsert, delete, plus bulk variants by primary key. Its fields are Table, Changeset, Filter-by and Primary key. A guard blocks writes to multiple rows unless you opt in.
- **REST query editor:** method, path, params, headers, cookies, and body (JSON, raw, form, multipart or binary). When a spec is attached it guides you through the operation.
- **Config variables and secrets:** per-environment values, referenced as `{{ retoolContext.configVars.X }}`. Secrets stay on the server.
- **Permissions:** Use / Edit / Own per group, on resources and resource folders, set per environment. Enterprise adds row and column **access policies** using user attributes.
- **Pooling and timeouts:** Postgres pools default to 10 connections; query timeout defaults to 120s (720s in workflows).

## 1.3 Workflows
- **Canvas model:**
  - Named **blocks** are joined by **connectors**, starting from `startTrigger`.
  - Fan-out runs in parallel. A block with several parents waits for all of them.
  - Every block exposes `name.data`, `name.error` and `name.metadata`. Any block that already ran can be read with `{{ }}`.
- **Block types:**

  | Block | What it does |
  |---|---|
  | startTrigger | `data`, `headers`, `pathParams`, `urlParams` from the trigger |
  | Resource query | Any resource, same editors as in apps |
  | Code | JS (Node 20, npm via package.json) or Python 3.x (requirements.txt), sandboxed with nsjail |
  | Branch | if / else-if / else, each with its own output connector |
  | Filter | iterable plus an expression on `value` / `index` |
  | Loop | runner = query / JS / function / workflow; parallel, sequential or batch(size, delay); per-iteration timeout, retries and error policy |
  | Function | Reusable subflow with named params; called from a Function block, `await fn()` in JS, or a Loop |
  | Workflow | Calls a child workflow, sync ("Finished") or async ("Queued") |
  | Response | HTTP status plus JSON body, the reply to a sync webhook or app call |
  | Wait | Durable delay, up to 60 days |
  | User Task | Human-in-the-loop. Assigns an app-based task to users or groups; the workflow resumes with its output. |
  | AI Action / Invoke Agent | LLM actions (generate, classify, extract…) and agents |
  | Global error handler | Unconnected block that runs on any unhandled error |

- **Settings on every block:** `timeoutMs` (default 10s), `retryCount`, `interval`, `exponential`, `coefficient`, `maxInterval`, and `finally` = stop or continue. "Continue" exposes a red **on-error** connector.
- **Triggers:**
  - **Manual**: the editor's Run button, using test JSON.
  - **Schedule**: interval or cron with a timezone; runs never overlap; jitter is added.
  - **Webhook**: `POST /api/workflows/:id/startTrigger` or an alias with `:params`, authenticated with an `X-Workflow-Api-Key` header. It is **synchronous if a Response block exists**. `?environment=` picks the environment.
  - Also: called from an app, called from another workflow, SQS/Kafka polling, and Retool platform events.
- **Context objects:** `workflowContext {currentRun, lastRun, lastSuccessfulRun, environment, triggerType}` and `retoolContext {configVars, secrets, users, groups}`.
- **Engine:** each run is a Temporal workflow. A worker calls code-executor (nsjail) for code blocks and workflows-backend for queries. Block results live in **Postgres or S3, not in Temporal**, because of Temporal's payload size limits.
- **Limits:**
  - Async runs: 30h. Sync runs: 15 min to the Response block.
  - 2.5 GB memory per run.
  - 50 in-flight requests per run.
  - 100 runs of a workflow per 15 min.
- **Versioning:** an autosaved **draft**, plus SemVer **releases**. Only the live release runs from schedules and webhooks.
- **Run history:** each run shows per-block status, logs, timing and data, with filters and JSON export. Default retention is 30 days.
- **IDE features:**
  - Run a single block, using cached upstream results.
  - Autolayout, minimap, README.
  - "Create function" from a selection of blocks.
  - Libraries tab, environment picker, AI-generated workflows.

## 1.4 Retool Database
- **What it is:** managed **Postgres** (self-hosted: a separate `retooldb-postgres`), exposed as a built-in resource named "Retool Database".
- **Spreadsheet-like editor:**
  - Tables list and tabs, inline cell editing, add or delete rows.
  - Filter, sort, hide and pin columns.
  - **Import CSV** or generate a schema with AI; export to CSV.
  - An `id` primary key is added automatically; foreign-key fields can open the linked row.
  - Field options: type, nullable, unique, default value (including SQL defaults).
- **Environments:** each environment gets its own isolated tables. Schemas are **migrated** between environments using a reviewed diff and generated SQL; data is not copied.

## 1.5 Apps (classic builder)
- **Layout:**
  - A **12-column grid** with fixed-height rows. **Frames** are Main, Header, Sidebar (240px), Modal, Drawer and Split pane.
  - **Containers** hold nested grids and support tabbed, stepped and multi-view variants. **Stack** is a flexbox container.
  - **List View / Grid View** repeat a template using `item` and `i`.
  - **Multipage** apps have global or per-page scope. **Modules** are reusable sub-apps with typed inputs and outputs.
  - A separate **mobile layout**, used below 600px.
- **Components:** about 100, grouped as buttons, Plotly charts, containers, forms, the Table, date, number, select and text inputs, presentation components, and special ones (file, signature, scanner, LLM chat).
  - Every component has an `id`, **properties** (configurable and runtime state), **methods** (`setValue`, `setHidden`, …) and **events**.
  - **Table** is the flagship component: selection, server-side pagination, filters and sort, editable cells (`changesetArray` → bulk-upsert query), row actions, grouping and export.
  - **Form** collects child `formDataKey`s into `form.data`, with validation and submit. It can be generated from a DB table, along with an insert query.
- **Reactivity:**
  - Every field can contain `{{ js }}`. All components, queries, transformers and variables are global identifiers.
  - A **dependency graph** re-evaluates the values that depend on a change, spreadsheet-style.
  - **Transformers** are pure.
  - **JS queries** have side effects: `query.trigger({additionalScope})`, `setValue`, and `utils.*`.
  - **Variables** hold temporary state; `localStorage` and `url` params are also available.
  - JS runs in a sandboxed cross-origin iframe with `_`, `moment`, `uuid`, `numbro` and `Papa` preloaded.
- **Queries in apps:**
  - Run behavior is **automatic** (reads and GETs) or **manual** (writes).
  - Options: run on page load, periodic runs, watched inputs, disabled-if, a confirmation prompt, throttle, timeout, cache TTL (on the server), and failure conditions.
  - Success and failure **event handlers** are how queries get chained.
- **Event handlers:** control query, control component, run script, go to app/page/URL, notify, set variable, set localStorage, set URL params, copy, export. Advanced options include "only run when", debounce and throttle.
  - Handlers on the same event run in parallel.
- **Reusing queries:** the **Query Library** offers org-wide versioned queries; apps can pin a version or follow the latest.
- **Serialization:** **Toolscript (`.rsx`)**, a JSX-like format:
  - `main.rsx` and `functions.rsx`.
  - Query bodies extracted to `lib/*.sql` and `*.js`.
  - **Layout stored separately** in `.positions/*.json`, which keeps diffs clean.
- **Releases and history:**
  - Every save is a history point. SemVer releases can be draft or published.
  - URL params: `_releaseVersion`, `_historyOffset`, `_environment`, `_embed`.
- **Extensibility:** custom component libraries are React built with a CLI and loaded in a sandboxed iframe through `Retool.useStateX` hooks. Also themes (tokens, light and dark), custom CSS, preloaded JS, Embed (signed single-use URLs for external users), and public apps.
- **Collaboration:** multiplayer editing (CRDT over WebSockets, last write wins, presence) and Debug Tools (console REPL, timeline, state and dependency inspector, linting, performance).

## 2.2 Workflow semantics (filling the gaps Retool leaves undocumented)

- **Block status:** `pending | running | succeeded | errored | failed | skipped | waiting | cancelled | interrupted`.
- **Edges** carry ports: `out`, `error`, `cond:<id>`, `else`.
- **Readiness:**
  - A block becomes ready when every incoming edge is resolved, and it runs if **at least one edge fired**.
  - If every incoming edge is dead, the block is `skipped`, and the skip propagates downstream (dead-path elimination). So a join after an if/else just works.
- **Branch:** only the first truthy condition fires. A condition that throws is a block error.
- **Errors:**
  - `finally=stop`: the run fails, in-flight sibling blocks are aborted, and the global error handler runs.
  - `finally=continue`: the block's `out` edge is dead and its `error` edge fires. To mean "always run C", connect both `out` and `error` to C.
- **References:** an expression may only reference static graph **ancestors** plus globals. Anything else is a lint error. A skipped ancestor evaluates to `{data:null, error:null, metadata:{status:'skipped'}}`.
- **Response:**
  - The first Response block sends the HTTP reply, and execution **continues**. Later Response blocks are marked `ignored`.
  - No Response reached: `200 {runId, status}`. Failure before a Response: `500`, unless the error handler contains a Response block.
- **Loop:**
  - `data` is an array the same length and order as the input.
  - `metadata.iterations[]` records each iteration's status.
  - Each iteration is checkpointed (`loop1[17]`), so a crash resumes without recomputing completed iterations.
  - `onError` is `stop` or `continue` (continue puts `null` in the failed slot).
- **Functions:** a subgraph with `params`. It returns the data of its return block. Called from a Function block, a Loop runner, or `await fn()` in JS.
- **Wait, sync child workflow, and User Task** persist the run as `waiting` with an `available_at`, which frees the worker slot. Time spent waiting doesn't count toward the run timeout (default 15 min, maximum 6h).
- **Delivery:** blocks execute at least once, and their outputs are committed exactly once (epoch fence plus unique `(run_id, block_key)`).
  - The scope exposes `idempotencyKey`.
  - Webhooks accept an `Idempotency-Key` header.
  - A run whose worker keeps crashing fails after 3 recoveries.
- **Schedules:** our own scheduler, rather than a library's.
  - `workflow_triggers.next_fire_at` holds the next fire time. Every worker ticks every 5s using SKIP LOCKED.
  - Overlap policy is `skip` (default), `queue` or `allow`. Runs are inserted with `ON CONFLICT (trigger_id, scheduled_for)`, so each fire happens exactly once.
  - After downtime the schedule catches up with one run, not a storm.
  - Timezone defaults to `Europe/Amsterdam`.

## 2.3 Data model (Drizzle, `packages/db`)
- **Identity:** `users`, `sessions`, `groups`, `group_members`, `permissions(group_id, object_type, object_id?, environment_id?, level)`, `environments`, `folders`.
- **Resources:**
  - `resources`
  - `resource_configs(resource_id, environment_id, config jsonb, secrets)`. In M1, `secrets` became one self-describing token `<keyVersion>.<iv>.<ciphertext>.<tag>` instead of separate ciphertext, IV and key-version columns; see `docs/handoff.md` §2.
  - `oauth_tokens` (M9): one row per resource config and owner (`user_id` null = the shared account): the encrypted tokens of an OAuth authorization-code connection, or a custom auth flow's variables; expiry, granted scopes, the account's label, `status` active/reconnect, and a fingerprint of the consent settings (or the flow) they belong to. `UNIQUE NULLS NOT DISTINCT (resource_config_id, user_id)`.
  - `config_vars` + `config_var_values` (per environment, optionally secret)
  - `api_keys` (prefix + sha256 hash, scoped to workflows and environments; built in M4 with expiry, revoke and last use). Runs record the key that started them (`workflow_runs.api_key_id`).
- **Workflows:**
  - `workflows(draft_definition, draft_revision, live_release_id, max_concurrent_runs)`
  - `workflow_draft_snapshots`
  - `workflow_releases(version semver, definition frozen, definition_hash)`
  - `workflow_triggers`: the runtime projection of the live release's triggers, holding the webhook alias and `next_fire_at`. M4: rows are matched by kind and name so ids survive releases; `alias_shape` (unique) keeps two live webhooks off the same URLs; `environment_id` and `last_fired_at` for schedules.
- **Runs:**
  - `workflow_runs`: status, input/output/error, lease fields, `available_at`, `idempotency_key`, `scheduled_for`, `parent_run_id`. In M2, `output` became `response` (the first Response block's reply), and each run points at exactly one release or draft snapshot. M5 added `suspended_at` (when a run paused; its deadline moves on by the time spent waiting) and `cancel_requested_at`. Child runs use `parent_run_id` and an idempotency key `child:<parentRun>:<block>:<attempt>`.
  - `block_runs(run_id, block_key, status, attempt, timings, error, metadata)`. M2 added `epoch` (the lease that wrote it) and `port` (the output that fired). M5: loop iterations are rows keyed `loop1[17]`; a `waiting` row's metadata holds `until` (and a child run's `childRunId` and `since`; M6: a User Task's `taskId`).
  - `block_run_payloads` (data jsonb, 10MB cap)
  - `run_logs`
  - `user_tasks` (M6): one per run and block; status `open | completed | expired | cancelled`; title, description, fields (defaults evaluated) and outcomes as they were when it opened; assignee user and group ids (resolved from emails and group names); `due_at`; the answer (`outcome`, `values`, `completed_by`, `completed_at`).
- **Audit:** `audit_events`, append-only; the app's DB role gets INSERT/SELECT only. M6: filters and a streamed CSV export for admins.
- **Managed database** (M7): `managed_databases(environment_id, schema_name, role_name)` records each environment's schema and role; `resources.system_kind` (`database`) marks the built-in `optiply_db` resource, whose per-environment `resource_configs` row logs in as that role. The tables themselves live in the `owdb_<environment>` schemas of the same database (§2.10).
- **Apps** (M8): `apps(slug, draft_definition, draft_revision, live_release_id, folder_id)` and `app_releases(version semver, definition canonical, definition_hash)`; `app` is a folder and permission object type (grants for every environment only). No draft snapshots: nothing pins an app's draft revision. App definitions are `@ow/app-definition`'s format (§2.11).
- **Git sync** (M11): `git_settings` (one row: repo URL, branch, the token and webhook secret encrypted together, and the deploy state: the deployed commit, the last check and error, the lease and pending request); `git_objects` (each workflow and app directory on the branch: the tree it last deployed, its status `deployed`/`problem`/`missing`, its problems, the version made live); `git_deploys` (each new commit deployed, or Deploy now: per-object outcomes; the last 200 kept); `workflows.git_protected` and `apps.git_protected`; `workflow_releases.git_commit` and `app_releases.git_commit` (releases made by Git sync, `created_by` null). More in §2.13.
- **Retention** (M6): once a day one worker (claimed through `maintenance_jobs`) deletes runs that finished more than `RUN_RETENTION_DAYS` (30) ago, and draft snapshots no run uses, at most 5,000 rows per statement, each its own transaction (payloads, then blocks and logs, then the run rows). Runs with an unfinished child are kept. `workflow_runs_finished_idx` finds them.

## 2.4 Workflow definition (`packages/definition`, zod v4)
- **Shape:** `{schemaVersion, settings, triggers{webhook, schedules[], manual}, blocks[], edges[], functions[], layout}`.
- **Block types:** `startTrigger`, `errorTrigger`, `resourceQuery`, `code`, `branch`, `filter`, `loop`, `function`, `workflow`, `response`, `wait`, `userTask`.
- **Settings on every block:** `{timeoutMs, retry{count, intervalMs, exponential, coefficient, maxIntervalMs}, finally}`.
- **Built for Git:**
  - Block **names** are the identity. Resources and child workflows are referenced by **slug**.
  - Layout is stored separately, and JSON is canonical.
  - `definition_hash` covers everything except layout.
  - No secrets appear in a definition.
- **Validator** (`validateDefinition()` returns diagnostics for the editor):
  - unique names
  - valid ports
  - no cycles
  - exactly one start trigger
  - expression identifiers are ancestors or globals
  - no Response block inside functions
  - each query passes its connector's `querySchema`
  - at release time, the publisher has Use on every resource in the target environments

## 2.5 Connectors (`packages/connectors`)
- **Interface:** `Connector { type, configSchema, secretsSchema, querySchema, ui, poolKey, createClient, destroyClient, testConnection, compile, execute, introspect? }`.
- **Pools:** a PoolManager holds them in an LRU and evicts idle pools. `NOTIFY resource_changed` invalidates them everywhere.
- **SQL `{{ }}` → bind parameters**, through one shared lexer that is aware of quotes and comments:
  - Postgres uses `$n` (arrays bind natively, so you write `= ANY({{ids}})`).
  - MySQL uses `?` and expands arrays.
  - BigQuery uses `@pN` named parameters.
  - A `{{ }}` inside a string literal is a validation error that suggests a fix.
  - **Sort columns (M10):** `{{ sql.column(value, ['name', 'price'], 'id') }}` and `{{ sql.direction(value) }}` become SQL text, not parameters. The compiler accepts them only as the whole `{{ }}` with the columns written as string literals (`sqlFragment`); the connector evaluates the value like any other (in apps, the browser sends it) and checks it against that list (or the fallback) before quoting it as an identifier for the dialect (`fragmentText`, `"p"."name"` or `` `p`.`name` ``) or writing `ASC`/`DESC`, all before the database sees the statement. `sql` is a stdlib global (server sandbox and app Worker), so it's a reserved name since M10.
  - Per-resource `disablePreparedStatements` is for Own/admin only (not built: every connector binds parameters).
- **MVP connectors:**
  - **Postgres** (postgres.js): `SET LOCAL statement_timeout`, cancel on abort, `maxRows`, optional read-only mode.
  - **REST** (undici):
    - Config: base URL, default headers and parameters, `allowedHosts`.
    - Auth: none, API key, bearer, basic, or OAuth2 client-credentials (tokens cached, refreshed once on a 401). M9: OAuth2 authorization code (shared or per-user accounts; tokens from the server through `QueryContext.credentials`) and custom auth flows (variables rendered into the resource's headers and parameters); see §2.12.
    - Bodies: json, form, raw or multipart.
    - Non-2xx responses error.
  - **MySQL** (mysql2, built in M6): server-side prepared statements, arrays expanded, `KILL QUERY` on cancel and timeouts, a read-only session option, `maxRows`, no local file reads.
  - **BigQuery** (built in M6 on the REST API with undici, not `@google-cloud/bigquery`): a service-account key (RS256 JWT), typed named parameters, `maximumBytesBilled` guardrail (10 GiB default), job labels for cost attribution (the resource's plus workflow, run and environment), the job cancelled on cancel and timeouts.
- **The built-in database resource** (M7): `optiply_db` is a Postgres resource the platform keeps configured per environment (§2.10); nobody can edit, re-point, rename or delete it, and testing it with other settings is refused (it would send the stored password elsewhere). Built-in resources list after people's own, so new query blocks keep defaulting to theirs.
- **Who runs as whom:** editor test runs use the editing user's Use permission. Released runs (schedule, webhook) were permission-checked when the release was published.

## 2.6 Monorepo layout (pnpm + Turborepo)
```
apps/
  web/      React editor + run history + resources UI (later: database editor, app builder)
  server/   main.ts ROLE switch → api/ (Fastify, tRPC, webhooks, SSE) · worker/ (claim loop, reaper,
            scheduler tick, retention) · cli/ (rekey, create-admin)
packages/
  definition/   zod schema, validator, graph utils, canonical JSON + hash           [web+server]
  git-format/   workflows and apps as repo files and back (M11)                     [web+server]
  expressions/  {{ }} parser, acorn free-identifier analysis, rename refactor, SQL lexer [web+server]
  engine/       orchestrator, block executors, scheduler, dispatcher (claim/lease/fast path)
  sandbox/      CodeRuntime, IvmRuntime, esbuild stdlib bundle + snapshot, host bridges
  connectors/   registry, PoolManager, postgres/ rest/ mysql/ bigquery/
  db/           Drizzle schema, migrations, repositories, LISTEN/NOTIFY helper
  crypto/       AES-GCM versioned keys + AAD, api-key hashing, secret redaction
  api-contract/ tRPC router types + REST zod/OpenAPI
  ui/           (planned; never created) the primitives live in apps/web/src/components/ui.tsx, shared with the app builder's renderers
```
- **Files that carry the design:** `packages/definition/src/schema.ts`, `packages/engine/src/orchestrator.ts`, `packages/engine/src/dispatcher.ts`, `packages/db/src/schema.ts`, `packages/sandbox/src/ivm-runtime.ts`, `packages/connectors/src/types.ts`.
- **Editor features:**
  - **Canvas:** React Flow nodes per block type, ports for `out`, `error` and `cond:*`, a dagre-based autolayout button, and a minimap.
  - **Inspector panel:** each block type has its own form. SQL and JS use Monaco, with a `.d.ts` generated from the last run's outputs so `query1.data[0].` autocompletes.
  - **Running:** Run (with test JSON), plus **Run block**, which uses the cached upstream outputs.
  - **Live status:** each block shows its status on the canvas, pushed over SSE.
  - **Run history panel:** filters, per-block data, logs, timing, and JSON export.
  - **Saving:** autosave with `draft_revision` (optimistic concurrency). A Releases tab handles publishing and rollback.
  - **App navigation:** the sidebar has Workflows, Resources, Runs and Settings (environments, groups, config vars, API keys, audit). Database and Apps are added in later phases.

## 2.10 The managed database (M7)

A Retool-Database-style store for tables people make and fill in the platform itself.

- **Where the tables live:** the platform's own Postgres, one schema per environment (`owdb_production`, `owdb_staging`). Each schema is owned by a **login role** of its own (`owdb_<md5(database)[:6]>_<environment>`; roles are shared by every database on a server, hence the tag) that has no rights on anything else: not the platform's tables, not the other environment's schema, and no role it could switch to.
- **Why a login role and not `SET ROLE`:** a query could switch back mid-statement (`set_config('role', …)`, then dynamic SQL such as `query_to_xml`), because the session user may always return to itself. So the role logs in with its own generated password, stored encrypted in the built-in resource's config like any secret and sent to Postgres as a SCRAM verifier (never as plain text).
- **Provisioning** (`apps/server/src/services/database.ts`) runs at every start (migrate and API), in one transaction under an advisory lock, and repairs drift: role attributes and password, roles granted to it by hand (revoked), schema and object owners (what a restore onto another server leaves), `CREATE` on `public` before Postgres 15. It needs superuser or `CREATEROLE`; without either it reports what to grant and the platform runs on.
- **Access:** Use on `optiply_db` in an environment is the whole of it (rows, schema and SQL), like Use on any resource, whose queries run with the resource's rights. A read-only tier would need a second, SELECT-only role and resource.
- **The schema editor** (`services/managed-db.ts`): tables always get `id bigint generated by default as identity primary key`; nine column types (text, integer, bigint, decimal, boolean, date, datetime, json, uuid; anything else made in SQL shows as "other"); defaults are a value or `now()` / `current_date` / `gen_random_uuid()`; type changes cast the values, all or nothing. Every statement runs as the environment's role, waits at most 5 s for a lock, and is audited.
- **Rows** (`services/managed-db-rows.ts`): pages with sort and 11 filter operators, counts capped at 10,000; values in JSON-exact shapes (bigint/decimal as strings, datetimes ISO in UTC, JSON as JSON); writes by single-column primary key, each value checked against its type first so errors name their field; values sent as text and cast in SQL (postgres.js would otherwise convert booleans, dates and JSON by its own rules).
- **CSV** (`services/csv.ts`, `services/managed-db-csv.ts`, `api/database.ts`): our own streaming RFC 4180 parser; a preview that guesses delimiter, names, types, date order and decimal commas; imports streamed as one line of JSON spec plus the file, all rows or none, problems reported by line and column; exports streamed with the grid's selection, formula-guarded in text cells only.
- **The web app:** `/database` (its own chunk): environments and tables, a TanStack Table 8 + Virtual grid (pages of 100 as you scroll, server-side sort and filter, in-place editing), the schema editor and the import wizard.
- **Not yet:** foreign keys and indexes in the editor, promoting a schema from staging to production (Retool's reviewed diff), a read-only tier, a separate database server for the managed tables.

## 2.11 Apps (M8)

Retool-style internal UIs: components on a grid, wired together with `{{ }}`, reading and writing data through queries.

- **The definition** (`packages/app-definition`): components (with a parent container and sparse props), queries (resource: a connector query plus `run: auto | manual`; JS: browser code), transformers and variables, sharing one namespace of JS identifiers; the layout apart from the logic; every string a template. The registry lists each component type's props (type, default), state (with the prop it starts from), methods and events. The canonical hash counts the layout (unlike a workflow's): moving a component is a change people see.
- **The reactive graph:** one node per readable value (`table1.selectedRow`, `query1.data`), with dependencies per property where the code names one (`freeIdentifierRefs(…, { properties: true })`), cycles found with Tarjan's algorithm, evaluation in topological order. A change re-evaluates only what depends on it and stops where a value comes out the same; input state restarts only when its default's value changes; an automatic query's `$deps` node tells it to run again.
- **Where code runs:** in the browser (Retool's way), inside a hidden iframe with `sandbox="allow-scripts"` (an opaque origin: no cookies, no access to the page) and a CSP without network access (`default-src 'none'`); it talks to the page over a MessageChannel. The page runs queries, keeps the state for React, and checks effects (http(s)/mailto links, text/CSV/JSON downloads). The sandbox's script (`@ow/app-runtime` plus the stdlib) is bundled by esbuild at build time and written into the frame's document. **Since M10 the app runs in a Worker** the frame starts from a blob: URL (the CSP adds `worker-src blob:`); the Worker inherits the frame's CSP (checked in Chrome, Firefox and WebKit: fetch, XHR, WebSocket, EventSource, `importScripts`, `import()` and nested workers all refused, nothing reaching the server), and refuses to start if a `data:` fetch isn't blocked. The frame passes the page's port on, so the page talks to the Worker directly. A watchdog pings it every second; one ping unanswered for 5 s (while the page's own timers run on time) removes the frame, which ends the Worker, and offers Restart. In the editor an edit restarts a stopped app.
- **Queries stay on the server** (`apps.runQuery`): the browser sends a query's name and the values of its `{{ }}`s (keyed by their code), never SQL; the server binds them as parameters, so values never become SQL. Expressions reading only `current_user` are evaluated on the server (what the browser sends is ignored); mixing `current_user` with app values is refused (validator and server).
- **Access:** Use on an app opens its live release and runs its queries without any grant on their resources; whoever publishes vouches for them (Edit on the app, Use on every queried resource in every environment), like a workflow's webhook. Draft queries (the editor) need Edit on the app and Use on the resource in that environment. A release that's no longer live is refused, so an open page can't keep running an old version. Manual (write) query runs are audited without values.
- **The editor** (`/apps/<slug>/edit`): react-grid-layout canvas (a grid per container, drag by handle), palette and tree, the inspector (props with `fx` switches, handlers), a bottom panel (queries, transformers, variables, state, problems, console), autosave with optimistic concurrency. The draft runs live and follows edits without restarting (typed values, query results and variables carry over; automatic queries re-run only when they or their values changed).
- **Components** (`apps/web/src/pages/apps/components`): Table (virtualized, sorting, selection, keyboard editing into `changesetArray` keyed by primary key, Save fires `save` and clears the changes once it succeeded), Form (`form.data` from its inputs, required inputs checked by the runtime), inputs, Button, Text, Container, Modal, and Chart (Chart.js in its own chunk; the dataviz reference palette in a fixed order, a table view).
- **Pages (M10):** optional `pages` (`{ name, title? }`, in order, the first opening by default) and an optional `page` on top-level components, queries and transformers; what names no page is global (components show on every page, above it; queries run on every page). Components inside a container are on its page; variables are always global. An app without `pages` is one page holding everything, so existing drafts and releases need no upgrade (no schema version bump). Code on a page reads what's global and what's on its page; global code reads only what's global; the same goes for event handlers' targets (`other_page` in the validator, with `unknown_page`, `duplicate_page` and `invalid_page`). `url` is built in (a reserved name, an entity in the graph so code reading it re-evaluates): `url.page` (the page shown, null without pages; an unknown page opens the first) and `url.params` (the URL's query parameters). `entityPages`, `defaultPage`, `resolvePage` and `pageVisible` in `packages/app-definition/src/pages.ts`. `edit` can't name a page (`/apps/<slug>/edit` is the editor). An app or workflow from before M10 with an entity or block named `url` or `sql` must rename it (the validator says so); until then a running app with its own `url` simply doesn't follow page changes.
  - **At run time:** the viewer is one route, `/apps/$slug/{-$page}` (two routes would remount the app between pages), and the router reads and writes search params as plain text (`URLSearchParams`, not TanStack's JSON). The page passes `url` (page, query string without `env`) with `start` and as `navigate` whenever the URL changes (links, Back, Forward); `AppRuntime.navigate` sets `url.*`, then runs the opened page's automatic queries that never ran or went stale while it was closed (an automatic query on a closed page only marks itself stale) and its run-on-load queries. `utils.openPage(page, { params, newTab })` checks the page and sends an `openPage` effect; the viewer changes the URL (or opens a tab), and the editor's host navigates in place. The canvas draws the global components' grid, then the page's.
  - **In the editor (M10 step 4):** the page being edited is the editor store's `url` (page and the params `utils.openPage` gave); the running draft follows it (`host.navigate`), and the host re-sends it after each definition update, since a page added or renamed may be navigated to before the draft has it. The pages panel calls the pure edits (`addPage`, which moves a pageless app's top-level components, queries and transformers onto `page1`; `renamePage`, which relinks Navigation; `setPageTitle`, `movePage`, `removePage` with `onPage`; `setEntityPage`); new components, queries and transformers get the edited page. The canvas has a frame grid (`grid-frame`, page null) and the page's (`grid-page`), each taking drops for its own page. Navigation (`items`: `{ page, label? }`, or every page; links to missing pages are an `unknown_page` error) opens pages through `host.openPage`, like `utils.openPage`.
- **Table paging, sorting and search (M10):** `paging` is `scroll`, `pages` or `server`; the pure `tableView` (search over the shown cells, ignoring case and accents, then sort, then the page, keeping each row's position in `data` for selection and edits) does it in the browser, and in `server` mode shows `data` as it came. State `page`, `sort` (`{ column, desc }`) and `searchText` (set through `setPage`/`setSort`/`setSearchText`, or the search box's acknowledged `set`; sorting and searching go back to page 0), and `pagination` (`{ page, pageSize, offset }`), a read-only node derived from `page` and `pageSize` like a form's `data`. Server sorting uses `sql.column`/`sql.direction` (§2.3).
- **Releases:** semver publish and rollback like workflows; `/apps/<slug>` shows the live release in an environment the viewer picks.
- **Folders for workflows and apps (M10):** `folders.*` takes the object type (`resource` when missing, as before): `list` returns a type's folders and `canManage`, creating, renaming and deleting need the type's create right (`canCreateResources`, `canCreateWorkflows`, `canCreateApps`), and a subfolder is of its parent's type. Deleting a folder sets what's in it to no folder (`ON DELETE SET NULL`) and removes the folder's grants. Moves still need Own and a folder of the object's type (`checkFolderMove`, since M8's review); folder grants stay admin-only. The web app's `components/folders.tsx` (`FolderSections`, `FolderSelect`, `NewFolderForm`, `useFolders`) is shared by the Resources, Workflows and Apps lists.
- **Not yet:** modules, a mobile layout, custom components, a Query Library, per-row column templates, multiplayer editing, themes per app (apps follow the platform's Optiply look, light or dark: §2.16).

## 2.12 Signing in to APIs (M9)

REST resources that act as a person or a workspace, or that have their own login.

- **OAuth 2.0 authorization code.** The settings hold the authorization and token URLs, client ID, scopes, extra consent parameters, client auth, PKCE (S256, on by default) and the token mode (`shared` or `perUser`); the client secret is with the other secrets. Presets (`@ow/connectors/oauth-presets`, browser-safe) fill these in for Google (offline access and a consent prompt, so a refresh token is issued), HubSpot, Slack (`ok: false` answers; user tokens in `authed_user`) and Microsoft 365 (a `{tenant}` placeholder; the scopes are sent again on refresh; refresh tokens rotate).
- **The connect flow** (`apps/server/src/api/oauth.ts`): `/api/oauth/start` (session; Edit for the shared account, Use for one's own) puts state, the PKCE verifier, the person and a fingerprint of the consent settings in a signed, HttpOnly cookie named after the state (10 minutes, path `/api/oauth`), then redirects to the consent screen. `/api/oauth/callback` (one redirect URI for every resource) needs that cookie, the same state and the same person's session, checks access and the consent settings again, exchanges the code and stores the tokens; it ends on a page that posts `ow:oauth` to the opener (`PUBLIC_URL`'s origin) and closes. Connects, disconnects and refused refreshes are audited without tokens.
- **Tokens in queries:** connectors ask the server through `QueryContext.credentials` (`accessToken({ force })`), so user tokens never sit in pooled clients; a 401 forces one refresh and a retry. Refreshes run under an advisory lock per owner, taken by trying and sleeping outside any transaction (waiters hold no connection), and whoever waited uses what the other stored: rotating refresh tokens are never spent twice. A refused refresh (`invalid_grant`) marks the row `reconnect` (committed) and later queries fail at once with `auth_required` (details: reason, shared/user, resource, environment), which the UI turns into Connect / Reconnect prompts. Changing the consent settings (including the token mode and where requests go: the base URL's origin and the allowed hosts) disconnects accounts, so a resource can't be pointed elsewhere to receive its token.
- **Whose account:** the shared one, or on per-user resources the person behind the query: the playground's caller, an app's viewer (who may connect their own account through the app, without access to the resource), a draft run's starter (the engine's `actingUserId`). Runs of a release have nobody behind them, so publishing (and rollback) refuses workflows that query a per-user resource.
- **Custom auth flows** (auth type `custom`): ordered steps (a REST request through the resource's base URL and allowed hosts without its default headers, JavaScript in the sandbox, or a variable), with `secrets.NAME` (named secret values), `auth` and earlier steps in scope; optional refresh steps (run on a 401 from the current variables, falling back to signing in) and `ttlSeconds`. The variables (`auth.NAME`) are rendered into the resource's headers and parameters on each attempt, scrubbed from results, stored encrypted in `oauth_tokens` (one shared row), and signed in for under a transaction-scoped advisory lock per config. Test connection signs in afresh in memory.
- **Not yet:** token revocation at the provider on disconnect, per-user custom flows (a form step), a back-off for a sign-in that keeps failing, live checks against the real providers (only the fake one so far), admin views of other people's connections.

## 2.13 Git sync (M11)

Retool's Source Control, for one instance and one GitHub repo: workflows and apps that matter are reviewed in a PR before they go live, and the repo is their history.

- **What's in the repo:** workflows and apps, nothing else (resources, folders and config vars stay on the instance; definitions already name resources by slug and hold no secrets). One directory per object, named by its slug, under `workflows/` and `apps/`, plus `ow.json` at the root (the format version). The files are the canonical definition with every code and SQL string moved into a file named after its block, query or transformer, so a PR diff reads like code:
  ```
  ow.json
  workflows/sync-orders/
    workflow.json        # name, description, settings, triggers, blocks, edges (canonical, no layout)
    layout.json          # canvas positions
    blocks/fetchOrders.sql
    blocks/transform.js
    functions/notify/blocks/send.js
  apps/order-admin/
    app.json             # name, description, components, queries, pages (canonical, no layout)
    layout.json
    queries/listOrders.sql
    queries/listOrders.transform.js
    queries/saveOrder.js
    transformers/rows.js
  ```
  `.sql` holds a resource query's `sql` (the `{{ }}`s stay as they are; a loop's query runner too); `.js` a code block's or a loop's code, a JS query's or a transformer's, and `<query>.transform.js` a query's transform. Other strings (REST queries, branch and filter conditions, props, event handler scripts) stay in the JSON. Files outside `workflows/` and `apps/` (a README, CI) are ignored. Files end with a newline that reading takes off again, so a value's own trailing newlines survive. A value written inline in the JSON (by hand) still reads; inline *and* in a file is a problem. Empty workflow layouts aren't kept (the same canvas); an app's layout is kept exactly, since it counts in the app's hash. `maxConcurrentRuns` isn't versioned and stays on the instance. Reading the files back gives the same canonical definition and hash (a property test over 400 generated workflows and apps); a file that doesn't parse, a missing or stray file, an invalid slug or a schema problem is a problem naming its path (and the path inside the JSON), and one broken object doesn't hide the others. Names that differ only in case give a warning (a macOS or Windows checkout would keep one file).
- **Protected objects** (`services/git/protection.ts`, M11 step 4a): an Own holder protects a workflow or app (`git.protect`). Its live release (or its draft, if it has none) is committed as its directory onto a branch (`protect/<kind>-<slug>` by default, from the deploy branch; an empty repo first gets a commit with `ow.json`, and `ow.json` is added when missing), and a pull request adds it to the deploy branch. **It's protected at once** (decided while building it: waiting for the merge would let main drift meanwhile), and merging deploys it (nothing new when it's what's live). On a protected object, main is read-only: saving the draft, renaming it or changing its description (the repo holds them), and publishing are refused (`PRECONDITION_FAILED`); its folder and concurrency limit stay the instance's. Making another release live is for admins only, as an emergency rollback until the next deploy (audited with `emergency: true`). `git.unprotect` (Own) lets it be edited here again; its directory stays in the repo and stops deploying (`not_protected`). Workflows and apps can also be created protected (`protected: true`), when Git sync is set up: edited on branches from the start, deployed by the first merge. Summaries carry `gitProtected`; release lists carry `gitCommit` (Git sync's releases have no `createdBy`).
- **Branches** (`services/git/branch-drafts.ts`, `branchDrafts.*`, M11 step 4b): repo-wide, named by people, made from the deploy branch. A protected object's editor picks a branch; each (object, branch) has its own draft on the instance (`git_branch_drafts`: definition, name, description, revision, the commit its files came from, whether the branch exists yet, the last commit), all with Edit on the object. **Open** loads the object's directory from the branch (or, with `create`, from the deploy branch: the branch is made by the first commit); where the repo doesn't have the object yet (created protected, or its protect PR isn't merged), it starts from the live release or the draft; a directory whose files have problems isn't opened (fix it in the repo). **Save** is optimistic like the main draft (schema checked, diagnostics back). **Run**: workflow runs and Run block take `draftId` and run a snapshot of the branch draft's revision (`workflow_draft_snapshots.branch_draft_id`, without a foreign key so runs outlive a discarded draft; retention keeps an open draft's current revision); `apps.runQuery` takes `branchDraftId`. **Changes** lists the files a commit would add, modify or delete against the branch's tip (texts up to 200 kB), and whether the branch moved (`behind`) or changed the object's files too (`conflict`). **Commit** (the revision the person is looking at) writes the object's directory onto the branch as one commit (message; author = the person's name and email; `ow.json` added if the base lacks it) and pushes; if the branch moved, it goes on top when the object's files didn't change there, and is refused otherwise (CONFLICT). **Update from branch** loads the branch's files into the draft (refused while it has uncommitted changes, unless they're discarded). **Discard** closes the draft; what's committed stays. **Open PR** (`git.openPullRequest`) opens the branch's pull request into the deploy branch, or returns the one already open; `git.pullRequest` finds it (open ones first) with its state and whether it merged; `git.branches` lists the repo's branches, the deploy branch first. A branch can carry several objects. The GitHub API (`services/git/github.ts`) is api.github.com for github.com and `<host>/api/v3` for GitHub Enterprise Server (`GITHUB_API_URL` overrides it, for tests), called with the repo's token, no redirects; its failures (not GitHub, no token, a refused token) come back as a message, not an error, so the branch is still there to open a PR by hand.
- **Deploy on merge** (`apps/server/src/services/git/deploy.ts`): GitHub's push webhook (`POST /api/git/webhook`, HMAC-SHA256 of the raw body with the webhook secret in `X-Hub-Signature-256`; JSON or form-encoded; `ping` answers, other events and branches are ignored; 404 without a secret) asks for a deploy, and workers poll the branch every `GIT_POLL_SECONDS` (60; 0 off). One deploy runs at a time across processes: a lease on the `git_settings` row; a request while another process deploys marks it, and the holder goes again when its round ends (at most 5 rounds). A deploy fetches the branch; an unchanged tip does nothing. Otherwise it reads `ow.json`, `workflows/` and `apps/`, decodes every directory (`@ow/git-format`) and compares each directory's tree with what it last deployed: an unchanged one is skipped while its object is still there and protected. Each changed directory creates its object (protected, no owner: admins grant access) or, for a protected one, updates its name, description and draft and, when the definition differs from the live release's, publishes a patch release made by Git sync (`created_by` null, notes = the commit's subject, `git_commit`) and makes it live, with every check publishing does except people's grants (validity, connectors' query checks, per-user accounts, schedule environments, webhook aliases). Workflows go first, then apps, in passes, so a new workflow can call another one new in the same commit. A directory whose slug belongs to an unprotected object isn't touched (`not_protected`). Problems (a file that doesn't parse, an invalid definition, a resource missing) skip that object and keep its live release; the rest still deploys. A directory that left the branch is flagged `missing` (the object stays). A repo without a readable `ow.json` deploys nothing. Deploy now (admins) re-checks every directory, for instance after creating a missing resource. Deploys are audited (`git.deployed`, and `<kind>.created` / `<kind>.release_published` with `source: git` and the commit, actor null).
- **Who may deploy:** writing to main (GitHub's branch protection and reviews) is the right to deploy protected objects; the instance doesn't check the merger's grants on resources. Committing from the instance needs Edit on the object.
- **Git itself** (`apps/server/src/services/git/`): the `git` CLI (in the runtime image since step 2; Debian's 2.39) on a bare cache repo per process (`GIT_CACHE_DIR`, default `<tmp>/ow-git-<pid>`; one directory per repo URL; one command at a time per process), with plumbing only: `ls-remote`, `fetch` of one branch, `ls-tree` + `cat-file --batch` to read files, a temporary index (`GIT_INDEX_FILE`, `read-tree`, `update-index --index-info`) + `hash-object`, `write-tree` and `commit-tree` to write, a fast-forward `push --porcelain` (`[rejected]`: the branch moved, fetch and retry; `[remote rejected]`: refused by the server, such as branch protection). No working tree, no checkout, no merge. `commitToBranch` writes directories onto a branch from the commit a change started from: it goes on top of a moved branch when none of the same paths changed there, and is a conflict otherwise; a lost push race tries again (3 times). Git runs with no system or global config, no credential helpers, no prompts, no hooks, `http.followRedirects=false` and only `https` (plus `http` and `file` with `GIT_ALLOW_INSECURE_URLS`, for development and tests). The token reaches git through `GIT_ASKPASS` (a script reading it from the environment of that one git process), never argv or the remote URL, and is blanked out of error messages. Errors are `auth`, `not_found`, `unreachable`, `refused` or `failed`. The GitHub REST API (pull requests, step 4) is called with the same token (a fine-grained token with Contents and Pull requests on the one repo). Settings (`git_settings`, one row, admins only, `git.*` in tRPC): repo URL (https, no credentials, query or fragment), branch (`main`), token and webhook secret in one encrypted value (AAD `git_settings:<id>:-`; covered by rekey and verify); the browser only sees whether they're set. Pointing the repo at another host needs the token again. Test connection signs in, reads the branch and counts the workflows and apps on it, and reports whether `ow.json` is there. Saving and clearing are audited (what changed, never the values). Tests use local bare repos (`file://`), `git http-backend` behind basic auth for the token path and a refusing hook, and a fake GitHub API (step 4).
- **The UI (M11 step 5a):** Settings → Git (admins): the repo URL, deploy branch, token (never shown; "Set", Remove) and webhook secret (generated in the browser, shown once to copy into GitHub, then only "Set"), Test connection, the webhook's payload URL and settings to paste into GitHub, and the deploys: the deployed commit, the last check and error, Deploy now, each directory's state (deployed version, problems by file) and the recent deploys (commit, the PR's title, what each object did). `git.info` (everyone) says whether Git sync is set up, the deploy branch and the repo's web address (https URLs without `.git`) for commit links. The Workflows and Apps lists show an "In Git" badge, a Protect button for owners (a dialog explaining what changes, the branch, then the commit and the pull request, or a link to open one by hand) and "Create it in Git" when making one. Release lists show "Git sync from <commit>" for deployed releases, and only admins see Make live on protected objects (an emergency rollback, said so in the confirm). Release notes of a deploy from a GitHub merge commit are the pull request's title and number, not "Merge pull request #N from …".
- **The editors (M11 step 5b):** a protected workflow's or app's editor has a Git bar (`components/git-bar.tsx`) under its header: a branch picker (the deploy branch, read-only; the object's open drafts and the repo's branches; New branch…), and the branch in the URL (`?branch=`). On the deploy branch the draft is read-only (the stores ignore edits: `readOnly`; no toolbar or palette, no autosave, no Publish) and still runs; a banner says to pick a branch. On a branch the editor loads the branch draft (`branchDrafts.open`, made if needed), autosaves through `branchDrafts.save`, and runs it (`draftId` on runs and Run block, `branchDraftId` in the app host's queries). The bar shows whether the branch exists yet, the last commit, whether the branch moved or conflicts (rechecked every 30 s), Update from branch (confirming when it drops uncommitted changes), the pull request and its state, and Close draft. Commit saves, then lists the files that change with a line diff each (`lib/diff.ts`: LCS with the common ends trimmed, unchanged stretches folded; texts over 3000 lines aren't compared), a message, and afterwards Open pull request (or the one already open). Switching back to the deploy branch fetches the object again (a merge may have deployed it). Settings: Protect in Git / Unprotect for owners (the workflow's Settings tab, the app's settings dialog); a protected app's name and description are read-only there (they live in the repo; changing them on a branch isn't in the editors yet).
- **Not yet:** GitLab and other hosts, resources and config vars in Git, promotion between instances, merging a branch draft with others' changes (update discards local ones), creating a brand-new object from the repo side only while editing (it appears on deploy).

## 2.14 Python (M12)

Retool's Python blocks, for workflows: data work (pandas, numpy) next to JavaScript, in a sandbox that holds nothing worth stealing.

- **Agreed with the user at the start of M12:** an **nsjail service** (a separate `code-executor` container running CPython; only it gets elevated privileges, and it holds no secrets), a **curated set of packages** baked into its image (adding one is a change to the image), and **data in, data out** (no network in the jail; no `fetch`, no workflow functions from Python: HTTP stays in REST resource blocks).
- **Where:** workflow Code blocks and loop code runners, in the main graph and in functions: `config.language: 'python'` / `runner.language: 'python'`, stored sparsely (absent means JavaScript, so existing hashes don't change). Templates (`{{ }}`), branch and filter conditions stay JavaScript; apps stay JavaScript (their code runs in the browser).
- **The code** is a function body, like JavaScript's: `return` gives the block's data (wrapped by the executor in a function; line numbers in errors are the block's own). In scope: the blocks it refers to, as variables with attribute and key access (`query1.data`, `query1["data"]`, `startTrigger.data`), `configVars` (non-secret ones in draft runs, as in JS), `workflowContext`, `idempotencyKey`, and `value`/`index` in loop runners, `params` in functions. The result must be JSON: dicts, lists, strings, numbers, booleans and `None`, plus `datetime`/`date` (ISO strings), `Decimal` and numpy scalars (numbers), NaN/infinity (`null`), a pandas DataFrame (a list of row dicts) and Series (a list); anything else is a `serialization` error. The 10 MB result cap applies. `print()` goes to the run log (`log`), `sys.stderr` to `error`, in the order written (the runner sends both through one pipe as tagged frames; bytes written to the file descriptors directly arrive untagged), at most 1 MB per execution (then cut off, said so).
- **Errors** reuse the sandbox's kinds: `syntax` (with the line), `runtime` (the exception's type and message and the line in the block's code, the traceback trimmed to the user's frames), `timeout`, `memory`, `serialization`. Retries, `finally` and the error handler work as for JS.
- **Finding references without a Python parser in TypeScript** (`analyzePython` in `@ow/expressions`, M12 step 2): a tokenizer (strings with every prefix, triple quotes, f-strings whose `{…}` fields are code, Python 3.12's nested quotes; comments; line continuations; implicit line joining in brackets) and a pass over the tokens. Not references: attributes (`a.b`), keyword arguments' names (`f(x=…)`), import statements' module paths, keywords, and **every name the code binds**, as Python's own rule is that a name bound anywhere in a function is local to it (assignments including tuple, chained, augmented and annotated ones, `for` targets in statements and comprehensions, `as`, `def`/`class`, parameters of `def` and `lambda`, imports, `:=`, `del`; `global`/`nonlocal` names stay references). Builtins (`len`, `sum`, Python 3.12's list) are kept apart: a block named like one can't be read from Python (warning `python_builtin`). What's left are the code's references: they decide the scope (only referenced blocks are copied in, as for JS), `self_reference` and `not_ancestor`, and renaming a block rewrites them (f-string fields included; a name the code binds or a builtin is refused as the new name, like a captured JS name). Nested functions and comprehensions count as part of the body (their bindings count everywhere), which only matters when a block shares a name with one of their variables. Checked against Python itself: a test compares it with `symtable` on a corpus of 38 realistic and tricky snippets (Python 3.12+ where installed; CI's runner has it). Never a syntax error here; there's no `unknown_identifier` for Python (a `NameError` at run time says it). Python's keywords JavaScript doesn't have (`None`, `pass`, `lambda`, `def`, …) become reserved block names (an existing block named so must be renamed, the validator says so); apps keep JavaScript's rules. A Python field naming `fetch` or a workflow function is an error (`python_unsupported`), and isn't counted as a function call.
- **Syntax:** the browser can't parse Python, so the server asks the executor to compile it (`POST /check`, `compile()` only, in a jail too): `checkDefinition` (before runs, at publish and Git deploys) adds `syntax` diagnostics with offsets, and the editor asks `workflows.checkPython` a second after a Python field stops changing, for markers.
- **The executor** (`apps/code-executor`, M12 step 1): a small HTTP server in Python's standard library (`executor/server.py`; nothing installed outside the jail) on `python:3.12-slim-bookworm`, with nsjail 3.6 built from source at a pinned commit (Apache-2.0; Debian doesn't package it) in a build stage, and the curated packages in a virtualenv (`/opt/py`) pinned with hashes (`requirements.in` → `requirements.lock` by pip-compile; releases at least two weeks old; numpy, pandas, python-dateutil, pytz, tzdata), pip removed afterwards. `POST /run { code, scope, timeoutMs }` → `{ ok, result | error, logs }`, `POST /check { fields: [{ id, code }] }` → `{ ok, problems }`, `GET /health` (Python and package versions); a bearer token (`PYTHON_EXECUTOR_TOKEN`, 16+ characters) shared with the workers and API; one jail per execution (`executor/runner.py` inside it); at most `PYTHON_MAX_CONCURRENT` at once (default the CPU count), others wait up to 30 s, then 503; a caller that hangs up (cancelled, timed out) has its jail killed; a refused request closes the connection (its unread body would be taken for the next request). No database, no encryption keys, no published port: only the app containers reach it. Structured JSON logs (one line per execution: path, ms, outcome).
- **The jail** (`executor/jail.cfg`): new user, PID, mount, network, IPC, UTS and cgroup namespaces; no network (a loopback, down); read-only `/usr` (with `/lib`, `/lib64` and `/bin` as symlinks into it: x86-64 binaries load through `/lib64/ld-linux-x86-64.so.2`, arm64 ones through `/lib`), the virtualenv, the runner and `/etc/ld.so.cache` (without `/proc` the loader can't find `libpython` through `$ORIGIN`), `/dev/null` and `/dev/urandom`, `/tmp` a 64 MB tmpfs (charged to the memory cgroup), nothing else: no `/proc` (a fresh procfs can't be mounted under Docker's masked `/proc` without more privileges) and no `/sys`; uid/gid 65534 inside **and outside** (not the executor's root); cgroup v2 limits on memory (256 MB without swap by default, `PYTHON_MEMORY_MB`), PIDs (32) and CPU (one); a wall-clock limit of the timeout rounded up to seconds plus one, the same CPU-time limit, and the server's own deadline 1.5 s later; rlimits (no core files, 256 open files, 16 MB files). A seccomp deny list on top of the container's profile (kafel): ptrace and reading other processes' memory, every mount call, `unshare`, `setns` and `clone` with namespace flags (`clone3` answers ENOSYS so libc uses `clone`), keys, bpf, perf, userfaultfd, modules, kexec, swap, reboot, io_uring; `fork` works. The environment is only `TZ=UTC`, `HOME=/tmp`, `LANG=C.UTF-8`, `PYTHONDONTWRITEBYTECODE=1`, `PYTHONHASHSEED=0`, `PYTHONUNBUFFERED=1`. Code and scope go in on stdin; the outcome comes back on its own pipe (whose fd is passed with `--pass_fd` and named in the request), so prints never mix with the result. Without an outcome, the error is `internal` when the jail never started (nsjail's own error, also in the executor's log), else a `timeout` (past the time), `memory` (killed otherwise) or the exit code.
- **What it costs** (step 1, on the Mac's Docker Desktop): a bare jailed interpreter 12 ms (nsjail adds ~6 ms), with `json`/`datetime`/`decimal` 19 ms, `import numpy` 58 ms, `import pandas` 213 ms; a trivial block over HTTP 39 ms p50 (78 ms p90). Each execution starts a fresh interpreter; a warm pool can come later if pandas' import cost matters.
- **The container's privileges** (step 1's spike): `--cap-add SYS_ADMIN` and a seccomp profile that is Docker's default plus `pivot_root` (`apps/code-executor/seccomp.json`, from moby/profiles); on hosts with AppArmor, `apparmor=unconfined` too (Docker's profile refuses nsjail's mounts). Not `--privileged`. The entrypoint remounts the container's cgroup writable (it can, with SYS_ADMIN), moves itself into a child cgroup and delegates the memory, PID and CPU controllers, so nsjail can give each jail its own. Without SYS_ADMIN nsjail can't create its namespaces; with Docker's default seccomp profile `pivot_root` is refused.
- **Engine and server** (M12 step 3): `PythonExecutorClient` (`@ow/sandbox`, a `PythonRunner`: `run` and `check` over HTTP with the token) is the engine's `services.python` (`RunExecutorOptions.python`, for the worker's Dispatcher and the API's InlineRunner); `runCode` picks by language (code blocks and loop runners), sends the block's scope as is (the blocks it reads, the run's globals, `value`/`index`, `params`) and aborts the request with the work (timeout, run failure, cancel), so the executor kills the jail; the logs come back with the result, a line each, and go through `work.log` like JavaScript's (scrubbed, a loop's prefixed with the iteration). Errors are `SandboxError`s: `syntax` ("… (line 1, column 11)"), `runtime` ("ZeroDivisionError: … (line 2)") with `details: { line, column?, traceback }` that reach the run's error, `timeout`, `memory`, `serialization`, and `unavailable` (the executor unreachable, busy, refusing, or unable to start a jail); retries apply like any failure. No executor: the block fails `python_unavailable`. Config: `PYTHON_EXECUTOR_URL` and `PYTHON_EXECUTOR_TOKEN` (16+ characters, required with the URL); the server keeps one client per process (`services/python.ts`, set up by the API and the worker at startup), so `checkDefinition` (before draft and live runs, at publish, rollback and Git deploys) adds the executor's `syntax` diagnostics (with offsets; one past the end marks the last character) or, without an executor or when it can't be reached, a `python_unavailable` error per Python field. `workflows.checkPython` (a mutation, as code can be long; any signed-in person) answers the editor: `{ available, problems | message }`. `pythonFields(def)` and `lineColumnOffset` (`@ow/definition`) find the fields and place the errors for both.
- **Git:** a Python code block or runner is `blocks/<name>.py` (`.js` stays for JavaScript).
- **The editor** (M12 step 4): the toolbar has "Add a Python code block" next to Code (named `python1`, … ; `return None` to start); a Python code block shows as "Python" with its own icon on the canvas and in the inspector (`kindOf`). The inspector's Language picker (code blocks and loop code runners) switches between JavaScript and Python keeping the text, and stores `language` only for Python. The editor is Monaco's Python mode on its own model (`code.py`, `runner.py`: JavaScript keeps `code.js`), with the validator's problems (ancestors, `python_unsupported`, `python_builtin`) at once and the executor's syntax errors a second after the code stops changing (`usePythonCheck` → `workflows.checkPython`; an answer for older code is dropped); when the instance has no executor, a note under the field says the code can't run here. Completions of blocks and globals, then `.data` and keys from the last run's values, as in `{{ }}` (without JavaScript's `_`, `dayjs`, `sql`).
- **Ops** (M12 step 5): a `code-executor` service in Compose (built from `apps/code-executor`; the only one with extra privileges: SYS_ADMIN, the seccomp profile, AppArmor off; `mem_limit` 2 GB, 512 PIDs, a health check; no published port) on an `executor` network that is `internal` and holds only it, the API and the workers, so the executor reaches neither the database nor the internet; the API and workers wait for it to be healthy. `PYTHON_EXECUTOR_TOKEN` is required in `.env` (like `SESSION_SECRET`); `PYTHON_MEMORY_MB` and `PYTHON_MAX_CONCURRENT` (4) pass through. CI's docker job builds its image too; server and engine tests start it like the MySQL container (`startTestExecutor` in `@ow/code-executor/testing`: builds this checkout's image, tagged by a hash of its sources, and runs it on a random local port; `PYTHON_EXECUTOR_TEST_URL`/`_TOKEN` to use another; skipped locally without Docker, required in CI); the e2e setup too. The runbook is `docs/runbooks/python.md` (configuration, privileges, adding a package, logs, symptoms).
- **Not in M12:** network access, `fetch` and workflow functions from Python, per-workflow packages, Python in apps, a Python debugger or step-through, keeping a Python process warm between blocks (each execution starts a fresh interpreter; step 1 measures what that costs).
- **From the PR #14 review** (session 12; these replace what's above where they differ):
  - **Runs don't wait for the executor's syntax check**: `checkDefinition(…, 'run')` only needs an executor configured (no network call), so a busy executor can't refuse runs, and a syntax error fails its block (with its line). Publishing, rollback and Git deploys still check the syntax.
  - **A check that fails says so**: `/check` answering `ok: false` (no jail, out of time) is `unavailable`, never "no problems". Checks time out after 15 s and runs after their timeout plus 35 s, if nothing else hangs up first.
  - **Timeouts keep the prints**: the client asks the executor to stop 500 ms before the block's timeout, and the executor's deadline is the timeout exactly (nsjail's whole-second limits a second later are the backstop), so it answers `timeout` with what the code printed; the message names the block's timeout.
  - **Checks have slots of their own** in the executor (`PYTHON_MAX_CHECKS`, 2): they never hold up runs. `workflows.checkPython` needs Edit on a workflow (`workflowId`), at most 20 fields of 200 kB.
  - **`del a[0]` and `del a.b` read `a`** (only `del a` binds it).
  - **Python's keywords aren't reserved block names** any more (JavaScript-only workflows from before M12 may use `pass` or `from`): in a workflow with Python they're a warning (`python_keyword`), and renaming a block Python reads to one is refused (the references wouldn't survive).
  - **Assigning a block's or run global's name** (`value = value * 2`, `rows = rows.data`, `configVars = …`) is a warning (`python_shadowed`): in Python that makes it the code's own variable, and reading it before fails with UnboundLocalError. (`from m import *` is a syntax error inside the function body: the executor's check says so.)
  - **Python is optional in Compose**: without `PYTHON_EXECUTOR_TOKEN` the app starts and Python stays off (a warning at start; blocks fail `python_unavailable`), the executor refuses to start; the API and workers start without waiting for it (`required: false`). A URL without a token is no longer a config error.

## 2.15 Editor polish (M13)

Undo, redo, copy, paste and duplicate in both editors, the way any editor has them.

- **Agreed with the user at the start of M13 (session 13):** M13 is undo/redo, copy/paste, duplicate and shortcuts in **both** editors; app modules and the Query Library are **M14** (each is a new object kind); AI actions go **last** on the roadmap.
- **History** (`apps/web/src/lib/history.ts`, pure: `record`, `undo`, `redo`): **snapshots of the definition**, not patches (every edit already returns a new object sharing what didn't change, so no dependency and no inverse-patch bugs). An entry is `{before, after, view}`; the view is what was selected (workflows: the block and the open function; apps: the component, the open code item and the page) and is put back on undo (a page through `resolvePage`; a function that no longer exists isn't opened). At most 100 entries. **Grouping** (automatic, decided in step 1: no keys at the call sites): `changeKey` compares the two definitions by reference and names the plain values the edit replaced (`.blocks.1.config.code`); consecutive edits with the same key, less than 1 s apart, merge (typing in a field, nudging a block); edits that change the shape (adding or removing blocks, edges or objects) never merge; undo, redo and a change of selection end a group. An edit that changes nothing (`sameValue`: some fields report the value they have) is ignored: no step, no save. A new edit drops the redo entries.
- **In the stores** (both): `update(edit)`, `undo`, `redo`. **To the server an undo is an edit like any other**: autosave saves it with the usual revision; history never holds revisions. `load()` clears the history (reloading after a conflict, switching branches, the Git bar replacing the draft). Undo is off while read-only or in conflict. The workflow store gets the app store's check against the saved JSON, so undoing back to what's saved doesn't save again. An `epoch` counter, raised by undo, redo and paste, keys the side panel, inspector and code panel: what they read once when mounted (name drafts, a trigger's test input, a default value, a request's JSON) and Monaco's models start afresh.
- **Shortcuts** (`apps/web/src/lib/shortcuts.ts`): Mod+Z, Mod+Shift+Z and Mod+Y, Mod+D (duplicate; the browser's bookmark shortcut is prevented), Delete as today; copy and paste through the browser's own events. Ignored in inputs, text areas, editable content, Monaco (`.monaco-editor`) and the side panel (`.nokey`), while a dialog is open and while composing (IME): **Monaco keeps its own undo**. Undo and Redo buttons in the toolbars.
- **The clipboard:** the `copy` and `paste` events (`clipboardData`: no permission prompt, so no Paste button, which would need `navigator.clipboard.readText`), copy skipped while text is selected on the page (run logs). The payload is JSON: `{ ow: 'workflow-blocks' | 'app-components' | 'app-queries', v: 1, … }`, so it works between workflows, between apps and between tabs. Copy works on read-only drafts; paste doesn't. **What's pasted is untrusted** (any page can put text on the clipboard): parsed with the definition schemas and a size cap; copying keeps the payload's hash in `localStorage`, and pasting anything else asks first, listing what will be added (in apps, how many queries run by themselves: the running draft follows edits within 300 ms).
- **Pasting blocks** (`packages/definition/src/paste.ts`: `copyBlocks`, `pasteBlocks`): names that are free in the target (not its blocks, functions or reserved words, nor the other pasted names, so renames never chain), given on a definition holding only the pasted items through `renameBlock` (references, edges and layout rewritten; a `captured` rename takes the next number). Edges are kept between pasted blocks only; positions are offset. The start trigger isn't pasted; a second error trigger, and blocks a function can't hold (the validator's `notInFunction`, exported), are skipped. **The functions the blocks call come along** (Function blocks, loop runners, calls in code; and the functions those call): added when missing, reused when the same (`canonicalJson`), the target's kept when different (said so). With exactly one block selected (not a branch), it's connected to the pasted roots, like Add. A summary lists what was skipped or reused and **the references to blocks that weren't copied** (they'd point at a block of that name in the target).
- **Selection on the workflow canvas:** `selection: string[]` in the store is **the only source** of what's selected (decided in step 2: mirroring React Flow's selection into the store and back looped). React Flow reports clicks, ⌘/Ctrl-clicks and box selection as `select` node changes; those go to the store (in the graph's order) and the nodes are rebuilt from it, so a multi-selection survives edits. A click also shows the block's inspector (`inspect`), without changing the selection. Copy, duplicate and delete use it.
- **Pasting in apps** (`packages/app-definition/src/paste.ts`: `pasteComponents` with their descendants, `pasteQueries` for queries, transformers and variables): fresh names in the app's one namespace through `renameAppEntity` (references, parents, handler targets, layout keys). Pasted into the selected component when it's a container (modals too), else next to it; overlays at the top level without layout; top-level items on the current page (global code stays global); the roots at the bottom of the grid they land in, keeping their offsets, children where they were in their container.
- **Fixed on the way:** the workflow editor loaded people with Use as editable (canvas edits went dirty and were never saved, and every refetch reloaded the draft); they now get it read-only, and a read-only canvas can't drag, connect or delete.
- **Not in M13:** modules and the Query Library (M14), selecting several components at once in apps, a Paste button, undo across reloads, pasting many cells in the Database grid.
- **As built** (steps 1–5): grouping is automatic (see History); the store is the only source of the canvas selection; both editors share `useEditorKeys` and `UndoButtons`; in apps, `focus` (the last component or code item chosen) is what copy and duplicate take; code clips (`app-code`) paste queries, transformers and variables onto the page being edited. The done-when ran in Playwright and on Docker Compose (handoff §9g, §10).

## 2.17 Modules and the Query Library (M14)

Retool's two ways of reusing app parts across apps: a query written once and used everywhere, and a piece of UI with its own queries placed like a component.

- **Agreed with the user at the start of M14 (session 15):** apps **reference** modules and library queries (slug plus a pinned version or `latest`), they aren't copied into the app's release; **whoever publishes a module or library query vouches for its resources**, like a workflow called by the Workflow block. Library queries are for **apps only** in M14 (workflows later). A module runs as an **isolated instance**: its own runtime and namespace, the app seeing only its inputs, outputs and events. **One milestone, the Query Library first** (smaller, and it sets the pattern for a new object kind), then modules.
- **Two object kinds, built like apps:** `library_queries` and `modules`, each with `slug`, name, description, folder, `draft_definition` and `draft_revision` (optimistic saves), `live_release_id` and `git_protected`, plus `library_query_releases` and `module_releases` (semver, the canonical definition and its hash, notes, `git_commit`, `created_by` null for Git sync). `library_query` and `module` join `PERMISSION_OBJECT_TYPES` and `FOLDER_OBJECT_TYPES` (Use, Edit, Own; folders; type-wide Edit to create them, `canCreateLibraryQueries`/`canCreateModules`), and `GIT_OBJECT_KINDS` (with a column each in `git_branch_drafts`). Audit: `library_query.*` and `module.*` like `app.*` (created, updated, deleted, release_published, release_live, protected, unprotected). The places that list kinds today (handoff §2 "Taken in M14" will list them) become one table of kinds where it's cheap, so a third kind later isn't another sweep.
- **What Use means:** Use on a module or library query lets someone **use it in an app** (an app's publisher needs it, and so does whoever runs an app draft that uses it); Edit opens its editor and runs its draft (with Use on its resources, as for an app draft); Own deletes it and manages grants. A viewer of an app needs nothing on what the app uses.
- **References and versions:** `{ library | module: <slug>, version: '<semver>' | 'latest' }` in the app's definition. A pinned version runs that release for as long as the app's release is live; `latest` runs the module's or query's live release at the moment of the run. Publishing an app needs Use on each referenced object, a live release for each `latest`, and the release for each pinned version (`unknown_library`, `unknown_module`, `unpublished`, `unknown_version` in the validator through `resolveLibrary`/`resolveModule`, given by the server and by the editor). **Deleting** a module or library query that an app's draft or live release references is refused, listing the apps (`usedBy`). Publishing a new release of one that apps follow on `latest` shows those apps first, and warns when it drops a parameter or input they pass.
- **The server still runs only what a release vouches for.** `apps.runQuery` gets a path: `{ query }` as today, or `{ module: '<instance>', query }` for a module instance's query. The server finds the query in the app's release (or draft); a `library` query resolves to its library release, a module instance to its module release (pinned, or the live one: the browser sends the module release it's running, and a `latest` instance whose module went live with another release meanwhile gets CONFLICT, "reload", like an app release that's no longer live). A query the resolved release doesn't have is NOT_FOUND. Resources are looked up from the release that holds the query, so the app's publisher can't point a library query at another resource.
- **Library queries** (`packages/app-definition/src/library.ts`): `{ schemaVersion: 1, resource, query, params: [{ name, description?, testValue? }], timeoutMs? }`. The query's `{{ }}`s read **only its parameters** (bare names: `{{ customerId }}`), `current_user` and the stdlib (`sql.column` included): no app state, so it means the same in every app (`unknown_identifier` otherwise). In an app: a query of `kind: 'library'` with `library`, `version`, `params: { <name>: <template> }` and the usual `run`, `transform`, handlers, `confirm` and `disabled` (a schema union member: no schema version bump, as with M10's pages). The browser evaluates the parameter templates and sends their values keyed by code, as today; the server evaluates them (`current_user` on the server), then evaluates the library query's `{{ }}`s in the sandbox with the parameters in scope, and binds the results as parameters (`untrustedValues`). A missing parameter is null; one the library query doesn't declare is a problem. The library editor: the resource, the query (the SQL editor or JSON for REST), the parameters with test values, Run (with the test values, as a draft run: Edit plus Use on the resource), releases, grants, Used by. In the app editor: Add query → From library (a picker), then a version (`latest` or a release), the parameters as fields with `fx`, the library query shown read-only, and Open in library.
- **Modules** (`packages/app-definition/src/module.ts`): an app definition **without pages**, plus `inputs: [{ name, description?, default?, testValue? }]`, `outputs: [{ name, description?, value: <template> }]` and `events: [{ name }]`. Inside, inputs are read as `inputs.<name>` (`inputs` is a built-in entity, like `url`; a reserved name in modules), outputs are templates evaluated in the module, and a handler action `moduleEvent { event }` fires one of its events. Modules use resource, JS and library queries like apps. **No modules inside modules in M14.**
- **A module in an app** is a component of type `module` (`props.module`, `props.version`, and one template per input, `props['input.<name>']`); the registry's spec for it is built from the resolved module (its inputs as props, its outputs as state, its events plus none of its internals), so the validator, the graph, the inspector and the completions treat an instance like any component. Instances sit on the grid like a container (their own 12 columns, the module's layout inside); `utils`, notifications and links work as in the app.
- **Isolated instances at run time:** the sandbox Worker runs **one `AppRuntime` per instance**, next to the app's, from the module release the page was given. The app's runtime evaluates the instance's input props and sets the instance's `inputs.*`; the instance's outputs come back as the instance's state (`customerPicker1.selectedId`), and `moduleEvent` fires the instance's event in the app's runtime. Values reach React under the instance's prefix (`customerPicker1/table1.data`), so two instances of one module never share state. The instance's queries go out through the same bridge with the instance's path. `apps.open` returns the live release with the definitions of the modules it references (resolved: pinned or live, with each release id); the editor resolves them through `modules.resolve` and follows a module's new release on reload.
- **The module editor** is the app editor in module mode (`/modules/<slug>/edit`): no pages panel; an Inputs/Outputs/Events panel; the inputs' test values feed `inputs.*` in the running draft. Publishing, releases, grants, folders and Git work as for apps.
- **Git** (`@ow/git-format`): `library/<slug>/` (`query.json`: name, description, resource, params, timeout; `query.sql` when it's SQL) and `modules/<slug>/` (like an app: `module.json`, `layout.json`, `queries/`, `transformers/`). Protection, branch drafts, Commit, Open PR and deploy on merge work as for apps; a deploy goes library queries, modules, workflows, then apps, so an app and the module it now uses can arrive in one commit. A deployed app is checked without people's grants (as today); its references must resolve on the instance after the earlier passes.
- **As built** (steps 1–8, handoff §9i): as designed above, with these choices made while building: a module is **an app definition with a `module` part** (not its own schema), so the validator, graph, rename and paste work on modules unchanged; outputs are `$outputs.<name>` nodes; an instance whose release isn't known yet has an open spec, so nothing flashes while the editor resolves it; per-kind Git behaviour lives in one table (`services/git/kinds.ts`). Not built from the plan: the publish dialog's warning when a new release drops a parameter or input that apps on `latest` pass (it says how many apps use it), and renaming a module input doesn't rewrite `inputs.<old>` reads (they show as problems). The done-when ran in Playwright and on Docker Compose (handoff §10).
- **Not in M14:** library queries in workflows, modules inside modules, a module's own pages, per-instance styling, library queries with JavaScript (they're resource queries), and pinning to a version range.

## 2.18 Webhooks for outside services (M15)

Today a webhook always needs one of our API keys, so services that sign their deliveries (Stripe, GitHub, Slack, HubSpot, Shopify) or can't send a header can't call a workflow. M15 closes that gap, plus body schemas, rate limits, multipart in and out, and an OpenAPI document.

- **Agreed with the user at the start of M15 (session 18):** a webhook authenticates callers with an **API key** (today's behaviour and still the default), a **signature** (HMAC, with presets), or **not at all (public)**. Signed and public webhooks are always rate limited, and making one public shows a warning in the editor. A webhook can declare a **JSON Schema** for its body. **Multipart both ways**: webhooks accept uploads, and REST queries can send multipart/form-data. **No queue triggers in M15** (SQS, Pub/Sub and Kafka stay in M16+).
- **In the definition** (`triggers.webhook`, no schema version bump: every new key is optional and its absence means today's behaviour):
  - `auth`: `{ type: 'apiKey' }` (the default), `{ type: 'public' }`, or `{ type: 'signature', preset, secret, … }`. `preset` is `stripe`, `github`, `slack`, `hubspot`, `shopify` or `custom`. `secret` is the **name of a secret config var**, so the signing secret is set per environment, encrypted like other secrets, and never in the definition or in Git. `custom` takes `header`, `algorithm` (`sha256`, `sha1`, `sha512`), `encoding` (`hex`, `base64`), `prefix` (e.g. `sha256=`), and optionally `timestampHeader` with `signedPayload` (a template over `{timestamp}`, `{body}`, `{method}`, `{url}`) and `toleranceSeconds` (default 300).
  - `bodySchema`: a JSON Schema (draft 2020-12) object for `startTrigger.data`. Its `pattern`s run on **RE2** in the server (`re2`, BSD-3; session 40): linear time on callers' input, so no lookarounds or backreferences (refused when the schema is checked, in the editor too).
  - `rateLimit`: `{ requests, windowSeconds }`. For signed and public webhooks it defaults to 60 per 60 s; for API-key webhooks the default is none.
  - `environments`: the environment slugs that `?environment=` may pick. For signed and public webhooks it defaults to the default environment only, so an anonymous caller can't pick staging. For API-key webhooks it defaults to all, and the key's own limits still apply.
  - `idempotencyHeader`: the request header to use as the Idempotency-Key when the caller doesn't send one. Presets fill it in where the provider has a delivery id (`X-GitHub-Delivery`, `X-Shopify-Webhook-Id`); a provider's retry of the same delivery then replays the earlier run. Not for public webhooks (the validator refuses one there).
  - The validator checks the shape of what people type (the preset's fields, a compilable schema, positive limits, known environments when they're given). **Publishing checks that the secret config var exists, is secret and has a value in each allowed environment**, as publishing checks resources today.
- **Presets** (verified with each provider's documented example in tests):
  - **Stripe:** `Stripe-Signature: t=…,v1=…`; HMAC-SHA256 hex of `{t}.{body}`; any `v1` may match; 300 s tolerance.
  - **GitHub:** `X-Hub-Signature-256: sha256=<hex>` of the body; idempotency from `X-GitHub-Delivery`.
  - **Slack:** `X-Slack-Signature: v0=<hex>` of `v0:{X-Slack-Request-Timestamp}:{body}`; 300 s tolerance. Slack's `url_verification` challenge is answered automatically once the signature passes.
  - **HubSpot (v3):** `X-HubSpot-Signature-v3`, base64 of HMAC-SHA256 of `{method}{url}{body}{timestamp}` (timestamp in ms, 300 s tolerance), the URL rebuilt from `PUBLIC_URL`.
  - **Shopify:** `X-Shopify-Hmac-Sha256`, base64 of the body; idempotency from `X-Shopify-Webhook-Id`.
- **The request, in order** (revised by the review, session 18):
  1. Find the webhook. No webhook at that URL is `401` for a caller without a valid API key (as before M15), so URLs can't be probed; `404` with a valid key.
  2. API-key webhooks: check the key (`401`) before anything else, so their methods and environments aren't revealed either.
  3. Public webhooks: check the rate limit (`429` with `Retry-After`); every call counts.
  4. Check the method (`405`) and the environment (`404`/`403`; and whether the API key may use it).
  5. Signed webhooks: check the signature over the **raw body bytes** with `timingSafeEqual` (the body parsers keep the raw buffer and parse only afterwards); on failure, `401` with a message that doesn't say which part failed.
  6. API-key and signed webhooks: check the rate limit. Only calls that authenticated count, so a flood of unsigned calls can't use up a signed webhook's limit and lock the real sender out (an HMAC-SHA256 can't be guessed, so throttling guesses buys nothing).
  7. Parse the body and check it against `bodySchema`; a mismatch is `400` with the first errors (path and message) and **no run**.
  8. Start the run as before. The signature header reaches the run like any header; API keys (`X-Api-Key`, `Authorization: Bearer ow_…`) never do. **Public webhooks ignore idempotency keys**: any caller could send another's key and read that run's reply.
- **Rate limits** are counted in Postgres (a table `webhook_rate_windows` keyed by trigger and window start; one `INSERT … ON CONFLICT DO UPDATE … RETURNING count` per call), so they hold across API processes. One limit per webhook across its environments (simpler, and a public webhook's limit is checked before its environment). Windows are fixed (aligned to the epoch, on the database clock), so up to twice the limit can pass around a window's boundary. Old windows are deleted by retention. Public webhooks are limited per webhook, not per IP: behind a proxy the caller's IP isn't reliable, and per-IP limits are a later option.
- **Rejections are visible.** Each 4xx a found webhook answers is recorded in `webhook_rejections` (only a window's first 429, and at most 60 a minute per webhook; calls refused before a webhook is found, such as an unknown URL or a body over 10 MB that Fastify refuses first, are only counted in the metric) (trigger, environment, time, reason code, a short message, the caller's IP and user agent; never the body or the signature), kept 7 days and capped at the last 200 per webhook. It's counted in `ow_webhook_rejected_total{reason}` and listed in the editor's webhook panel. That's how someone setting up Stripe sees "signature didn't match" or "timestamp too old" without reading server logs.
- **Body schemas** are compiled with **Ajv** (MIT, with ajv-formats) once per release and cached by the release's hash. The editor also uses the schema to type `startTrigger.data` for completions (the same JSON Schema → TypeScript translation the runs' types use) and can draft a schema from a sample body.
- **Multipart in** (webhooks): `multipart/form-data` is parsed with busboy (MIT) from the raw buffer. Node's own parser (undici's `Response.formData`) was tried first and refuses valid bodies whose boundary text appears inside a part. Fields arrive as strings and files as `{ filename, contentType, size, base64 }` in `startTrigger.data`; a name sent more than once becomes an array, and a part without a Content-Type is `text/plain` (RFC 7578). At most 1,000 parts (`413` beyond). The body limit is the app's 10 MB for every webhook body (over it, Fastify answers `413`). Base64 makes files ⅓ larger and results are capped at 10 MB, so a file a block returns whole can be about 7 MB.
- **Multipart out** (REST queries): a fourth body type, `{ type: 'multipart', parts: [{ key, value } | { key, file, filename?, contentType? }] }`. `file` is a template that evaluates to a base64 string or to a `{ base64, filename?, contentType? }` object (the shape webhooks deliver), so a received upload can be forwarded unchanged. It's sent with undici's `FormData`, which sets the boundary itself. The REST query editor gets a Multipart tab.
- **OpenAPI:** `GET /api/v1/openapi.json` is an OpenAPI 3.1 document listing the live webhooks the caller may call (an API key sees the workflows it's limited to; a signed-in user sees the workflows they can view), with their paths, alias parameters, methods, auth (an `apiKey` security scheme; signed and public webhooks are described in their text), body schema and the `202`/`429` answers. It also covers `GET /api/v1/runs/{id}`. The trigger panel and Settings → API keys link to it. Tests validate it against the OpenAPI 3.1 schema.
- **Git:** the new keys are part of the definition, so they travel in `workflow.json` unchanged; the secret's value never does. A deploy whose secret config var is missing on the instance is reported like a missing resource.
- **As built** (session 18, handoff §9j): as designed above, with these choices made while building: rate limits are **per webhook** (not per webhook and environment), since the limit is checked before the environment; multipart uses busboy as planned after Node's own parser (undici's `Response.formData`) refused valid bodies whose boundary text appears inside a part; the 10 MB body limit was already app-wide; the refused-calls list keeps only a window's first 429 and at most 60 rejections a minute per webhook, and is shown to Edit; a secret config var may hold several secrets, one per line (rotation); REST queries' file parts take base64 or the webhook's file object; the OpenAPI document is served by the runs API (which already authenticates a session or an API key). The done-when ran in Playwright and on Docker Compose with two API processes (handoff §10).
- **Not in M15:** queue triggers (SQS, Pub/Sub, Kafka); per-IP limits; the `?api_key=` query parameter (signatures cover the callers that can't send headers); asymmetric signatures (e.g. ed25519 or JWT-signed webhooks); listing runs with an API key; outgoing webhooks (a workflow calling out is a REST query).

## 2.19 Multiplayer editing (M16)

Today one person edits a draft at a time: each save sends the whole definition with its revision, and a second editor gets "someone else changed this workflow, reload". M16 lets several people edit the same workflow or app together.

- **Agreed with the user at the start of M16 (session 18):** the **workflow and app editors** (modules come along: the module editor is the app editor; the library query editor stays single-user); text in code and SQL fields **merges as people type**, with each person's cursor and selection shown in Monaco; presence shows **avatars, what each person has selected, and live mouse pointers** on the canvas.
- **A Yjs document per draft** is the shared truth while anyone has the editor open: the workflow's (or app's) main draft, or a Git branch draft (M11), keyed `workflow:<id>`, `app:<id>`, `module:<id>` (modules have their own table) and `branch:<branchDraftId>` (a Git branch draft of any of the three). The editors keep their immutable `definition` and every editing function (rename, paste, add, validators) unchanged:
  - **Local edits** still produce a new definition; a diff of before and after is applied to the Yjs document as minimal changes (`@ow/collab`): objects as `Y.Map`, arrays as `Y.Array` matched by identity (blocks and functions by `name`, edges by `from`/`port`/`to`, components and queries by name, conditions by `id`; others by position), **text fields as `Y.Text`** (code, SQL, templates: any string field an editor shows in Monaco, listed per editor), other strings and numbers as values (names, types, ids: last writer wins, never character-merged).
  - **Remote changes** turn the document back into a definition, sharing every unchanged part with the previous one (so React and the canvas only redraw what changed), then validate it as today.
  - Property tests: two (and three) replicas apply random editor edits concurrently, sync in random orders, and converge on the same definition, which passes the schema.
- **Undo and redo are one's own** (Yjs `UndoManager` with the local origin): undoing never reverts someone else's edit. M13's behaviour carries over: typing in one field groups into one step (the capture timeout is M13's 1 s), a change of selection starts a new step, and undo shows what it undid (the view kept with each stack item). Monaco fields bound to a `Y.Text` use the same manager, so ⌘Z in a code field undoes one's own typing there.
- **The connection:** a WebSocket per open editor, `GET /api/collab/<key>` (the session cookie; Edit to write, Use to watch read-only; a protected main is read-only for everyone, as today), speaking the y-protocols sync and awareness messages. Fastify with `@fastify/websocket`; the browser reconnects with backoff and resyncs (Yjs merges whatever was typed offline).
- **The server** keeps each open document in memory in the API process that has a connection for it, and:
  - **persists** every update in Postgres (`collab_updates`: key, id, the update; compacted into its `collab_documents` row, which belongs to the workflow, app, module or branch draft and goes with it, when 200 pile up or the last person leaves), so a document survives restarts and moves between processes;
  - **relays** updates and awareness between API processes with `NOTIFY` (the update's row id; awareness, small, in the payload), the run events' approach;
  - **materializes the draft**: at most once a second while edits flow (and when the last person leaves), the document's JSON is checked against the schema and written to `draft_definition` with `draft_revision` + 1, so runs, Run block, publishing, Git commits and the problems list see what the editors see. A merged document that fails the schema (it shouldn't: every edit is schema-valid, and the merge rules keep it so) isn't written; the editors show the last saved state as "couldn't save: …" and the server logs it;
  - **folds in other writes**: a REST or tRPC `saveDraft` (an API client, an old tab) and a Git pull into a branch draft are applied to an open document as a diff, so nothing is lost and nobody gets a conflict.
- **Presence** is y-protocols awareness: the person (name, avatar, a colour from a fixed palette), the editor's selection (block names or component names, and the open graph or page), and the mouse pointer in canvas coordinates (sent at most 20 times a second, dropped after 30 s without movement). The header shows avatars (with "and n more"); a selected block or component gets an outline and a name tag in its person's colour; pointers are drawn on the workflow canvas and the app grid in canvas coordinates, so they line up whatever each person's zoom; Monaco shows others' cursors and selections.
- **Saving in the UI** becomes a connection state: "Saved" (the server has every local change), "Saving…", "Offline: changes will sync" (reconnecting), "Read only". The CONFLICT path disappears for collaborative editors; `ensureSaved` (Run waits for it) waits until the server has acknowledged the local changes and materialized them.
- **Not in M16:** the library query editor and the resource playground (single-user); comments; following someone's view; history of who changed what (the audit log keeps saves); offline editing across a reload (unsent edits survive a reconnect, not a closed tab).
- **As built** (sessions 19–20, handoff §9k): as designed above, with these choices made while building: the document is a `SharedDefinition` (`@ow/collab`): `.value` reads it back with structural sharing and `.set(next)` writes the difference against the document itself, arrays matched along a longest common subsequence (by identity, or by content for positional arrays), an object whose `type`/`kind` changes replaced whole, and positions (canvas, grid) as one value; `SharedHistory` wraps the UndoManager with M13's grouping. Storage is `collab_documents` (one per draft, with its owner and cascade) and `collab_updates`, not `collab_snapshots`. A Postgres trigger on the draft revisions NOTIFYs every draft writer, so REST saves, release restores, Git deploys and pulls are folded in without touching their code. The browser asks for a save (`MESSAGE_SAVE`, answered with the draft's revision or the schema error), which is what `ensureSaved` waits for, and the server sends a status message. Monaco is bound by our own binding (`text-binding.ts`), not y-monaco (which manages models itself and fought `@monaco-editor/react`); app fields whose text is parsed into the value (props, a variable's initial value, a resource query's JSON, library params) merge as values. Access is re-checked every 30 s on an open socket and when it changes the socket closes with code 4403 and a reason (a refused upgrade looked like a network failure to the browser, which retried forever). The done-when ran in Playwright and on Docker Compose with two API processes (handoff §10).

## 2.20 SSH tunnels for resources (M17)

Today a resource connects straight to its host. Optiply's production database is reachable only through an SSH server, so connecting it needed a manual `ssh -L` on a Mac. M17 lets a resource connect through SSH by itself.

- **Agreed with the user at the start of M17 (session 20):** the SSH settings are **part of each resource configuration** (per environment), not shared SSH profiles; an SSH server's **host key is trusted by confirming it in Test connection** (never silently on first use); **Postgres, MySQL and REST** resources can use a tunnel (BigQuery stays direct: it's Google's API); **jump hosts are in M17**.
- **Settings:** an optional `ssh` part of the config of Postgres, MySQL and REST resources: `hops`, the SSH servers in the order they're connected to (the first reached directly, each next one through the one before; the last opens the connection to the resource's host and port; at most 3: the server and two jump hosts), each `{id, host, port (22), username, auth: 'key' | 'password', hostKey?: {algorithm, fingerprint}}`. The secrets are per hop and write-only like the database password (`applySecretPatch`, masked as `{set: true}`), kept under each hop's stable `id` so removing a jump host shifts nothing: `ssh: {<hop id>: {privateKey, passphrase} | {password}}`; on save, secrets of hops that are gone, and those a hop doesn't sign in with, are dropped. A key is read when the config is saved or tested, so a wrong passphrase or an unreadable file is refused then, with why; the settings show each key's type, its SHA256 fingerprint and its public half (the `authorized_keys` line, not secret).
- **Keys:** OpenSSH (`BEGIN OPENSSH PRIVATE KEY`, bcrypt-encrypted too) and PEM (RSA, EC, PKCS#8) through `ssh2`'s parser; **PuTTY `.ppk`** through our own reader (`ssh2` 1.17 reads only version 2 with RSA or DSA): versions 2 and 3, RSA, Ed25519 and ECDSA, unencrypted or `aes256-cbc` (version 3 derives its key with Argon2, `node:crypto`'s `argon2Sync` in Node 24; the MAC is checked, so a wrong passphrase says so), converted to OpenSSH form before `ssh2` sees it.
- **Host keys:** `ssh2`'s `hostVerifier` compares each server's key with its hop's `hostKey`. No pin: refused (`ssh_host_key_unknown`, with the fingerprint); a different key: refused (`ssh_host_key_changed`, both fingerprints). Test connection returns each hop's key and status; **Trust** puts the fingerprint into the form, saved with the settings (pinning needs the same right as editing them). The settings form clears a hop's pin when its host or port is edited; the server keeps a pin as sent (what's trusted is the key: another server presents another one, which is refused).
- **Tunnels** (`packages/connectors/src/ssh/`), in-process: no local port is opened. A `SshTunnel` is the chain of `ssh2` clients for one resource configuration and version, each next hop connected over `forwardOut` from the one before; `open(host, port)` returns a duplex stream (`forwardOut` on the last hop) for the driver. The pool's client owns its tunnel (made with it, closed with it: `PoolManager` already keys clients by configuration and version and drops stale ones), so the API process and each worker have their own. Keepalives every 15 s (3 missed: dead); a dead chain is reopened on the next `open`, with a 15 s connect limit per hop, so queries during an outage fail with a connection error rather than hang, and come back by themselves once the server is back.
- **Drivers:** porsager `postgres`'s `socket` option (it layers TLS on the stream itself), `mysql2`'s `stream` factory (also for the side connection that cancels a query with `KILL QUERY`), and for REST an undici `Agent` whose `connect` opens the tunnel (and TLS over it for `https`, with the hostname for SNI and certificate checks). A tunnelled REST resource skips the private-network guard: what it reaches is the SSH server's network, which is the point. Everything the connector sends for the resource goes through its tunnel, an OAuth2 client-credentials token included (changed while building: the token endpoint may itself be internal); the OAuth authorization-code flows run in the server, outside the connector, and stay direct.
- **Test connection** reports steps: each hop (connected, host key, signed in) and then the database or HTTP check, each with its time and error (`ssh_connect`, `ssh_auth`, `ssh_host_key_unknown`, `ssh_host_key_changed`, `ssh_forward`, then the connector's own codes).
- **Secrets stay secret:** keys, passphrases and passwords are decrypted only in the process that opens a tunnel, never returned by the API (only `{set: true}`, the key's type, fingerprint and public half), added to `scrubSecrets` for errors and logs, and `ssh2`'s debug output is off.
- **Ops:** `ow_ssh_tunnels_open` and `ow_ssh_tunnel_reconnects_total`; a log line (no secrets) when a tunnel opens, drops or reconnects; a runbook (`docs/runbooks/ssh-tunnels.md`: making a key, `authorized_keys`, `AllowTcpForwarding`, trusting a host key, rotating).
- **Tests:** an in-process `ssh2` `Server` as a test SSH server (password and key users, its own host key, forwarding to embedded Postgres, the MySQL container and a local HTTP server, a jump mode, restartable), in the connector and server tests and the e2e setup; key fixtures made with `ssh-keygen` and PuTTY's `puttygen` (committed test keys); the Compose check against a real OpenSSH server in Docker.
- **Not in M17:** SSH agent forwarding or keys from a local agent (the server has no agent); certificates (`ssh-*-cert`); keyboard-interactive or 2FA logins; SOCKS or HTTP proxies; shared SSH profiles across resources; tunnels for BigQuery.
- **As built** (session 20, handoff §9l): as designed above, with these choices made while building: secrets are kept per hop under a stable hop `id`, not position, so removing a jump host shifts nothing; pins aren't dropped by the server when a hop moves (the review, session 20: what's trusted is the key, and dropping one re-trusted for the same server lost it; the form clears it on an edit); `ssh2` also reads neither PKCS#8 nor the EC PEM `ssh-keygen -m PEM` writes, so PEM and PKCS#8 keys are converted through `node:crypto` like `.ppk` ones; mysql2 wants its stream at once (`deferredStream`), and postgres only ends a socket whose `readyState` is `'open'` (tunnel channels get one); a tunnelled REST resource's client-credentials token goes through the tunnel (changed from the plan); log lines come from a process-wide event hook, subscribed once per process. The Compose check against real OpenSSH found that a server behind a jump host going away only ends its channel (OpenSSH closes it after an EOF back, and ssh2 stops that hop's keepalives on `end`), so a hop's `end` is a drop too, and the test SSH server now behaves like sshd. The done-when ran in Playwright and on Docker Compose against real OpenSSH (handoff §10).

## 2.21 Google Cloud IAP for SSH (M18)

Optiply's production database sits behind an SSH server (`bastion`, GCP project `clear-veld-186016`, `europe-west1-c`) that has no public SSH port: it's reached through Google Cloud's Identity-Aware Proxy, today with `gcloud compute start-iap-tunnel bastion 22 --local-host-port=localhost:2222` running on someone's Mac and the resource's SSH host set to `host.docker.internal:2222`. That works only while the command runs, on that one machine. M18 makes IAP a way for the tunnel itself to reach its first SSH server.

- **Agreed with the user at the start of M18 (session 21):** IAP reaches **a VM by name** (project, zone, instance, a port; no destination groups or private IPs); the Google identity is **a service account key or the server's own identity** (both).
- **Where it sits:** IAP replaces only the TCP connection to the **first** hop. SSH runs over it unchanged: the same user, key or password, host key pin and jump hosts after it (M17's `connectHop` already takes a ready `sock`). The first hop gets `reach: 'direct' | 'iap'` (default `direct`, so M17 configs are unchanged); with `iap` it has `iap: {project, zone, instance, interface ('nic0')}` instead of `host`, and its `port` is the VM's SSH port that IAP connects to. Host keys are pinned per hop as before (the fingerprint is the VM's sshd's, whatever the transport).
- **The protocol** (as in the Cloud SDK's `iap_tunnel_websocket*.py`): a WebSocket to `wss://tunnel.cloudproxy.app/v4/connect?project=…&zone=…&instance=…&interface=nic0&port=22&newWebsocket=true`, subprotocol `relay.tunnel.cloudproxy.app`, `Origin: bot:iap-tunneler`, `Authorization: Bearer <access token>`. Binary frames start with a 2-byte tag: `CONNECT_SUCCESS_SID` (1, then the session id), `RECONNECT_SUCCESS_ACK` (2, then 8 bytes: what the server got), `DATA` (4, then a 4-byte length and at most 16 KiB), `ACK` (7, then 8 bytes: total bytes received). We ack once more than 32 KiB is unacked, and keep what we sent until the server acks it. **A dropped WebSocket resumes** at `/v4/reconnect?sid=…&ack=…` with a fresh token, resending what wasn't acked (bounded: past a few MiB unacked the stream fails and M17's tunnel reopen takes over). Close codes become our errors: a 401/403 handshake or `4033` → `iap_auth`; `4047` (instance not found) and `4003` (nothing listening on the port, or a firewall missing `35.235.240.0/20`) → `iap_target`; `4004` (reauthenticate) → resume with a new token; the rest → `iap_connect`. In `packages/connectors/src/ssh/iap.ts`: `openIapStream(target, getToken, {signal})` → a `Duplex`, over undici's `WebSocket` (already a dependency; custom headers through its init).
- **Google identities** (`packages/connectors/src/google-auth.ts`, BigQuery's token code moved there and shared): a **service account key** (JSON, validated like BigQuery's; a signed JWT for a `cloud-platform` token; the key's own `token_uri` ignored) stored encrypted in the hop's secrets (`ssh.<id>.iapKey`), or **the server's identity**: `GOOGLE_APPLICATION_CREDENTIALS` (a `service_account` key or an `authorized_user` file from `gcloud auth application-default login`, refreshed at `oauth2.googleapis.com/token`), else the metadata server (`GCE_METADATA_HOST`, default `metadata.google.internal`). Tokens are cached per identity and refreshed a minute before they expire.
- **Who may use the server's identity:** it reaches whatever the server's account may reach, so it's off unless the instance opts in (`GOOGLE_SERVER_IDENTITY=allow`), and only admins can save a configuration that uses it (editing other settings of such a configuration keeps working for its editors; switching to it, or changing its IAP target, needs an admin). With a service account key, the key is the permission, so editors may use it as they may any secret.
- **Test connection** gets an IAP step before the first hop ("Google IAP: bastion (clear-veld-186016, europe-west1-c):22 · ms"), with the identity used (the key's `client_email`, or "server identity: <email>" where known) and its error code and a hint (`iap_auth`: the identity needs `roles/iap.tunnelResourceAccessor` on the VM or project; `iap_target`: the instance name, zone, port, and the firewall rule for `35.235.240.0/20`).
- **M17 follow-up in this milestone:** an SSH host of `localhost`, `127.0.0.1` or `::1` refused with `ECONNREFUSED` adds a hint: in Docker, `localhost` is the container; a tunnel on the host is `host.docker.internal`.
- **Secrets and ops:** the service account key is a secret like an SSH key (never returned: `{set: true}` and its `client_email`; in `scrubSecrets`); access tokens are never logged; a counter `ow_iap_resumes_total` next to `ow_ssh_tunnel_reconnects_total`; the SSH runbook gains an IAP section (the service account, its role, the firewall rule, `GOOGLE_SERVER_IDENTITY` and mounting a credentials file into Compose).
- **Tests:** a fake IAP endpoint in `ssh/testing.ts` (a WebSocket server speaking the subprotocol, checking the token and target, forwarding to the in-process test SSH server, able to drop a connection, demand a reauth or refuse with each close code), fake token and metadata endpoints; the connectors' tunnel tests, the server's resource tests and the e2e through them. The real thing once by hand against Optiply's bastion (only with the user's go-ahead: it's production).
- **Not in M18:** IAP to private IPs or other ports without SSH (destination groups); IAP for BigQuery or REST without SSH; the server's identity for BigQuery (it could reuse `google-auth.ts` later); mTLS (`mtls.tunnel.cloudproxy.app`, for BeyondCorp-enforced setups); workload identity federation files (`external_account`).
- **As built** (session 22, handoff §9m): as designed above, with these choices made while building: Test connection's IAP line reads "Google Cloud IAP to project/zone/instance:port · as <identity>", the identity being `describe()` (a service account's email, the VM's from the metadata server, or "gcloud application-default credentials (a user)" for an `authorized_user` file, which has no email); a stored key shows as its `client_email` in `iapKeys`, next to M17's `sshKeys`, rather than inside the secret mask; the admin rule is on the **target** (project, zone, instance, interface, port of a server-identity hop), on save **and** on Test connection (unsaved settings open the tunnel too), and editors keep such settings and change the rest; `checkSshIap` runs the tunnel's own checks on save, so save and connect can't disagree; the network interface (`nic0`) isn't in the form; `GOOGLE_IAP_URL`/`GOOGLE_TOKEN_URL` point the server at fakes in tests; `ws` (the WebSocket client) is declared in the server too, which the bundle needs (it was missed in step 3a and found by the server build in step 5a); Compose gets an optional `docker-compose.gcloud.yml` that opts in and mounts the host's gcloud application-default file. The done-when ran in Playwright through the fake IAP endpoint (with control routes to drop WebSockets and refuse connects) and on Docker Compose against Optiply's real bastion with the server's identity from the user's `gcloud auth application-default login` (handoff §10).

## 2.22 Pub/Sub triggers (M19)

Workflows start today from the editor, a webhook, a schedule or another workflow. Services that publish events to a queue rather than calling a URL can't start one, and a webhook needs a public address the Compose stack on a Mac doesn't have. M19 adds Google Cloud Pub/Sub, the queue Optiply's GCP projects would use.

- **Agreed with the user at the start of M19 (session 22):** **Pub/Sub only** (SQS and Kafka later, as more kinds of the same trigger); workers **pull** from a subscription (no push endpoint); a message is **acked when its run succeeds**, nacked when it fails, so Pub/Sub's own redelivery, backoff and dead-letter topic apply; the connection is a **Pub/Sub resource** that triggers name (and that workflows can publish through).
- **The resource** (`packages/connectors/src/pubsub.ts`, type `pubsub`): config `{project, identity: 'key' | 'server'}`, secret `serviceAccountKey` (the BigQuery pattern); the identity through `google-auth.ts` (M18): a key's tokens, or the server's own (off unless `GOOGLE_SERVER_IDENTITY=allow`; only admins may save a resource that uses it, as for IAP). Per environment like every resource. Test connection checks the identity and lists a topic or subscription it can see. Queries (workflows, apps): **publish** `{topic, messages: [{data, attributes?, orderingKey?}]}` → the message ids. The REST API (`pubsub.googleapis.com/v1`) over undici, not gRPC: `subscriptions.pull`, `acknowledge`, `modifyAckDeadline` (a nack is a deadline of 0), `topics.publish`, `subscriptions.get`. `PUBSUB_EMULATOR_HOST`-style endpoint override for tests and the emulator.
- **The trigger** (`triggers.pubsub`, up to 20, no schema version bump): `{name, enabled, resource (slug), subscription (id or full name), environment (slug; the default one if left out), maxInFlight (1–100, default 4), maxHoldMinutes (how long a message is held while its run lasts, default 60)}`. Projected from the live release into `workflow_triggers` (kind `pubsub`, a migration for the kind and run trigger type checks) like schedules: kept by name across releases, deleted when a release drops it; Git sync carries it with the definition.
- **The consumer** (`packages/engine/src/pubsub-consumer.ts`, in each worker next to the Scheduler): one process at a time holds a **lease per trigger** (a row lease like the Git deployer's, renewed while pulling; another worker takes over when it lapses), pulls up to `maxInFlight − held` messages, starts a run per message and holds its ack deadline (extended every so often, up to `maxHoldMinutes`); when the run ends, success → acknowledge, failure or cancel → nack (deadline 0). Past `maxHoldMinutes` the message is acked and the run goes on (logged, counted). A run's `input`: `{data, attributes, messageId, publishTime, orderingKey, deliveryAttempt, subscription}`, `data` parsed as JSON when it is JSON, else text (`dataBase64` too for binary). Run trigger type `pubsub`.
- **Deliveries and duplicates:** a table `pubsub_deliveries (trigger_id, message_id, runs, last_run_id, outcome)`. A delivery starts a run with idempotency key `pubsub:<trigger>:<message>:<n>` (the delivery's number for that message), so a consumer that retries after a crash doesn't start two; a message whose run **succeeded** is acked on sight; one whose run is **still running** (its consumer died, the deadline lapsed) is held again, not run twice. Pub/Sub is at-least-once: a message acked whose ack was lost comes back and is acked without a run.
- **Ordering keys:** Pub/Sub delivers a key's next message only after the one before is acked, so a subscription with ordering runs a key's messages one at a time, in order, with no work of ours.
- **Ops:** metrics `ow_pubsub_messages_total{outcome}` (`acked`, `nacked`, `duplicate`, `released` past the hold), `ow_pubsub_in_flight`, `ow_pubsub_pull_errors_total`; log lines (`component: pubsub`: lease taken or lost, pull errors with Pub/Sub's message, held past the limit); the trigger's state in the editor (pulling on which process, in flight, last message, last error); a runbook (a subscription, its ack deadline and dead-letter policy, the roles: `roles/pubsub.subscriber` on the subscription, `roles/pubsub.publisher` on topics; with Compose, `docker-compose.gcloud.yml`).
- **Tests:** a fake Pub/Sub endpoint in `packages/connectors/src/testing.ts` (topics, subscriptions with an ack deadline and redelivery, `deliveryAttempt` with a dead-letter policy, ordering keys, a way to fail a call), connector tests, consumer tests against the fake and Postgres (redelivery, hold, lease takeover, in-flight limit, duplicates), the done-when in Playwright through the fake, and by hand a real topic and subscription on Docker Compose.
- **Not in M19:** push subscriptions; SQS and Kafka; exactly-once delivery subscriptions (Pub/Sub's own feature; our duplicate check covers acked messages); batching several messages into one run; schema-validated topics beyond passing `data` through; Pub/Sub for BigQuery or Cloud Storage notifications beyond what a subscription delivers anyway.
- **As built** (session 22, handoff §9n): as designed above, with these choices made while building: a run's input is `{data, message}` (`startTrigger.data` the message's data, `startTrigger.message` the rest, like a webhook's body and headers) rather than flat; run ends are **polled** (one query per trigger and second, only while holding) rather than LISTENed; a held message's deadline is set to 60 s at once (a subscription's own is often 10 s) and every 20 s; `stop()` nacks what a worker holds so the next one gets it at once; one worker takes every free trigger (no spreading); the trigger's state (in flight, last message, last error) is written to `workflow_triggers.state` on each lease tick for the editor; releasing needs Use on a trigger's resource in every environment, as for queried ones; Pub/Sub resources are checked on save (a key, or the server's identity allowed and a project), and M18's admin rule covers them (`pubsub:<project>`); the delivery records are pruned after 32 days. Found while building: the editor's triggers form rebuilt the triggers from webhook and schedules only (Pub/Sub triggers would have been dropped by any edit there), and workflow code has no `setTimeout` (the done-when's slow runs use a durable Wait block). The done-when ran in Playwright through a fake Pub/Sub and on Docker Compose against a real topic and subscription in `optiply-workflows`, with the server's identity (handoff §10).

## 2.23 Three-way merge for Git branch drafts (M20)

Today a branch draft (§2.13) and its branch can't both change: **Update from branch** is refused while the draft has uncommitted changes (or drops them), and **Commit** is refused when the object's files changed on the branch since the draft's base. And when two branches change the same object, the second pull request conflicts on GitHub with main, where a line merge of `workflow.json` is all GitHub can offer. M20 merges definitions the way people think of them: block by block, component by component, code line by line.

- **Agreed with the user at the start of M20 (session 23):** of M11's gaps, only the **three-way merge** (resources and config vars in Git, the editor gaps and the deploy follow-ups wait); real conflicts are resolved by **picking a side per conflict** in a dialog (code and SQL can also be edited by hand), nothing saved until all are resolved; and **Update from main** brings the deploy branch into a branch as a real merge commit, so the pull request becomes mergeable.
- **The merge** (`packages/collab/src/merge.ts`, pure, used by the server and the web): `merge(spec, base, ours, theirs)` → `{ merged, conflicts }`, driven by the same `CollabSpec` that says how M16 maps a definition onto Yjs, so both agree on what an item is:
  - **Objects** merge key by key; a key changed on one side takes that side; changed the same way on both, it's clean.
  - **Arrays with an identity** (blocks and functions by name, edges by their ends, components, queries, pages, event handlers by id…) merge item by item: added on one side → added; deleted on one side and untouched on the other → deleted; **deleted on one side and changed on the other → a conflict on the whole item**; added on both with the same identity → merged as two changes from an empty base (a conflict where they differ). An item whose `type` (or, for an app query, `kind`) differs between the sides is merged whole (its config would mix two kinds). The merged order is ours, with theirs' additions placed after the item they follow there.
  - **Text** (the spec's text paths: code, SQL, templates, expressions) merges **line by line** with diff3 (`node-diff3`, MIT, no dependencies): changes to different lines both apply; overlapping changes are a **text conflict** carrying each hunk's base, ours and theirs, and the text around them.
  - **Atomic values** (a canvas position, an app grid item) and arrays without an identity are values: changed on one side → that side; on both, differently → a **value conflict**.
  - A conflict has an `id` (a hash of its path and the three sides), its `path`, a label for people (`block fetchOrders · config.sql`, `component table1 · props.data`) and its sides. `resolve(result, resolutions)` applies `{ [id]: 'ours' | 'theirs' | { text } }` (a text conflict: one choice per hunk, or the whole field edited by hand); a resolution whose id no longer exists is ignored, so a resolution only ever applies to the conflict the person saw.
  - The object's **name and description** merge as values beside the definition. A library query (no M16 editor yet) gets its own small spec: its SQL and body as text, parameters by name.
  - The merged definition is checked against the kind's schema, with the unresolved conflicts left at ours and again at theirs (so it doesn't matter which side is which); the innermost item both sides changed around a failure becomes a whole-item conflict (two sides' changes that don't fit together, like a Wait block switched to "until" on one side while its duration changed on the other), else the definition's key, else the whole definition. Problems the validator finds (an edge to a block the other side deleted, a reference to a renamed block) aren't conflicts: they show in the editor as any problem does, before committing.
  - **Renames** aren't followed: a block renamed on one side and edited on the other is a deleted and changed item (a conflict on it) plus an added one. The rename's rewrites of other blocks' references merge as text.
- **Update from branch** (`branchDrafts.updateFromBranch`, server): base = the object at the draft's base commit (or what the draft started from on the instance, when the base had none), ours = the draft, theirs = the object at the branch's tip. Clean → the merged draft is saved with the tip as its base (one revision), and open editors fold it in as they do today's update (M16: applied to the Yjs document as a diff, so nobody's typing is lost). Conflicts → nothing is saved; the conflicts come back with the tip they were computed against. The person resolves them and calls again with the resolutions and that tip: the server merges **again** from the draft as it is now (others may have typed meanwhile), applies the resolutions, and saves only if no conflict is left (new ones come back). A save racing the merge retries the merge (up to 3 times) instead of failing. `discardChanges` stays, for "throw mine away".
- **Commit** keeps its rule: a commit never includes changes the person hasn't seen. When the branch changed the object meanwhile it's still refused, and the editor's Commit says "Update from branch first" (now a merge, not a loss), then commits. `branchDraftChanges` adds whether updating would merge cleanly or how many conflicts it has, so the Git bar can say so before anyone clicks.
- **Update from main** (`branchDrafts.updateFromMain`): for a branch that exists, it merges the deploy branch into the branch as **one merge commit** made by the person (parents: the branch's tip and main's tip), from the **committed** sides:
  - `git merge-base` of the two tips is the base. Every object directory both sides changed since then is merged with `merge` (decoded, merged, encoded again); conflicts come back grouped by object, for the same dialog (resolving one needs Edit on its object; one without Edit refuses the whole update, naming it).
  - Everything else is merged by `git merge-tree --write-tree` (git 2.38+; the image has 2.39), with the merged object directories written over its tree. A conflict outside an object directory (a README, a CI file) refuses the update, naming the paths: fix it on GitHub.
  - The commit is pushed as a fast-forward of the branch (a moved branch: try again from the start). Then the current editor's draft is updated from the branch by the three-way merge above, so its uncommitted changes stay (rarely, with conflicts of their own). Other drafts on the branch see that it moved, as they would after anyone's commit.
  - For a branch not made yet (the draft's first commit creates it), there's nothing to merge: the draft is merged three-way onto main's tip and takes it as its base.
  - The Git bar shows **"main changed this <kind>"** when the deploy branch has commits the branch lacks that touch the object's directory (rechecked with the other state every 30 s), with Update from main.
- **Plumbing** (`services/git/repo.ts`): `mergeBase(a, b)`, `mergeTree(ours, theirs)` → `{ tree, conflicts }` (`--write-tree --name-only -z`, in the bare cache, no working tree), `commitTree(tree, parents, …)` with directories written over a tree, `isAncestor`. The rest as in §2.13: no checkout, no working tree.
- **The merge dialog** (`components/merge-dialog.tsx`): the conflicts grouped by block, component, query or object; for a value, Mine / Theirs side by side (JSON for objects); for text, each hunk with the lines around it and Mine / Theirs / Both (mine then theirs), plus **Edit by hand** (Monaco, starting from the merge with each hunk's current choice); a counter of what's left; Apply once every conflict is resolved. It never saves anything itself: Apply sends the resolutions, and conflicts that came back new replace the list.
- **Tests:** property tests over the generated workflows and apps of M11's round trip and M16's convergence tests (merging with an unchanged side gives the other side; the same change on both sides is clean; `merge(b, x, y)` has the same conflicts as `merge(b, y, x)`, sides swapped; resolving every conflict with ours gives ours where theirs changed nothing else); hand-written cases for every rule above; server tests against local bare repos (update with and without conflicts, resolutions after a concurrent save, Update from main producing a two-parent commit whose `merge-tree` into main is clean, conflicts outside objects refused); the done-when in Playwright; by hand, against a real GitHub repo once (the PR mergeable after Update from main).
- **Not in M20:** following renames across a merge; merging an unprotected object's main draft (there's no branch); resources, folders and config vars in Git and the other M11 gaps; GitLab; rebasing a branch instead of merging main into it.
- **As built** (session 23, handoff §9o): as designed above, with these choices made while building: resolutions are passed **into** `merge()` / `mergeObject()` (no separate `resolve`), so merging again from a draft that changed meanwhile and applying the person's choices are one call; a conflict's id hashes its kind, `at` and three sides (cyrb53 ×2), so a choice never applies to a conflict that changed; unresolved conflicts sit at ours in `merged`; an identity array with a missing or repeated identity merges as a value; an app query's `kind` counts like a block's `type`; the schema check runs on the merge with conflicts left at ours **and** at theirs (with ours only, whether a misfit was found depended on which side was which: found by the property tests); the three sides are normalized through the Git format (encode → decode) before merging, so a draft and files compare alike; Update from branch's `discardChanges` never retries a racing save (dropping changes the person hasn't seen isn't theirs to do), the merge retries 3 times; Update from main's resolutions are keyed by object directory, then conflict id; an object directory deleted on one side and changed on the other is refused (fix it on GitHub), as are files with problems; resolving conflicts in an object not on the instance is for admins. `GitRepo` got `mergeBase`, `isAncestor`, `mergeTree` and merge commits (`tree`, `mergeParents`; made even with the first parent's tree). The Git bar saves what's typed before merging, and Commit becomes "Update, then commit" while the branch changed the object. The shared `Dialog` no longer closes on an Escape pressed in a Monaco field (it closed the merge dialog and lost its choices: found by the e2e). Diff3, like git, makes changes on adjacent lines one conflict. Checked against a real GitHub repo (handoff §10): the second PR conflicting on GitHub became mergeable after Update from main, and both changes deployed.

## 2.24 Reuse everywhere (M21)

M14 (§2.17) made library queries and modules for apps, and left out what makes them reusable everywhere: workflows can't use a library query (a workflow copies the SQL into a Resource query block), a module can't hold another module, and the library query editor is single-user while every other editor is multiplayer (M16). M21 closes those, with four small M14 gaps.

- **Agreed with the user at the start of M21 (session 24):** library queries in workflows as **a new block type** (and a loop runner kind), not a mode of the Resource query block; **`current_user`** in a workflow is **whoever started the run** (child runs inherit it; null for schedules, webhooks and Pub/Sub); modules nest **three levels at most** below an app, and **cycles are refused**; and four of M14's gaps come along (renaming module inputs, instances on hidden pages, the "needs Use" message, the publish warning about dropped parameters and inputs).
- **The library definition moves to `@ow/definition`** (`library.ts`: the schema, `checkLibraryQuery`, `libraryScope`, `LibraryInfo`), re-exported by `@ow/app-definition`, so the workflow validator and the engine use it without depending on apps.
- **The Library query block** (`type: 'libraryQuery'`): `config: { library: <slug>, version: '<semver>' | 'latest', params?: { <name>: <template> } }`, with a block's usual settings (timeout, retries, error handling). A loop runner `{ kind: 'library', library, version, params? }` sees `value` and `index` as other runners do. The parameters are templates over the run's scope (blocks, globals, `params` in a function); the library query's own `{{ }}`s read only its parameters, `current_user` and the stdlib, as in apps. Its data and metadata are a Resource query block's, plus `library: { slug, version }` (the release that ran). The validator takes `resolveLibrary` (the same `LibraryInfo` as apps): `unknown_library`, `unpublished`, `unknown_version`, a parameter the release doesn't declare, and `no_use_access` (below); the graph reads the parameter templates; rename, paste, the canonical form, M16's collab spec (parameters as text fields) and the Git format treat the block like any other (no separate files: it has no code of its own).
- **Who vouches:** as in apps. Publishing a workflow release needs Use on every library query it uses (and a live release for each `latest`, the release for each pinned version); then whoever runs or triggers it needs nothing on the library query, whose release says which resource and query run (its publisher vouched for them). A draft run needs Use on the library query (not on its resource). `latest` resolves when the block runs; a retry of the block resolves again.
- **`current_user` in a run:** the run's `created_by` (manual runs, editor runs, runs started from an app or the REST API by a person), copied to child runs (Workflow blocks, loop workflow runners) and kept across waits and User Tasks; null for schedules, webhooks (API keys, signatures, public) and Pub/Sub. The engine gets it as `{ id, email, name } | null` with the run, through a new `EngineServices.library` (`resolve(slug, version)` → the release's version, resource, query, parameters, timeout; a `BlockFailure` `library` when unknown or unpublished). Library queries are the only place a workflow reads `current_user`: it isn't added to the workflow's own scope.
- **Used by:** a library query's `usedBy` (deletion refused, the publish dialog's count, the editor's Used by) lists workflows (draft or live release) besides apps and modules. Git deploys already go library queries first.
- **Modules inside modules:** a module may hold module instances, the `nested_module` problem replaced by two: **`module_depth`** (an app holds modules of depth 3 at most, a module holds modules one shallower than its own limit; a module's depth is 1 plus the deepest module it holds, through the releases it references, `latest` as the live one) and **`module_cycle`** (a module reaching itself through the modules it holds). `ModuleInfo` gains each release's `depth` and the slugs it reaches. Both are checked by the validator (editor and server) and **when publishing a module**: a new live release must not make a cycle or a chain too deep for any app or module that follows it on `latest` (refused, naming them). The editor's module picker leaves out what would be refused.
- **Nested instances at run time:** an instance's `AppRuntime` starts its own instances from the same module release map (`apps.open` and `modules.resolve` return every release reachable from the app, pinned or live, stopping at the depth limit as a guard); page-side names nest by `/` (`picker1/search1/table1.data`). A query's module path becomes a chain, `[{ instance, releaseId }, …]`, and the server walks it: the app's release (or draft) holds the first instance, whose module release (pinned, or live for `latest`: a different release id gets CONFLICT "reload") holds the next, and so on to the query; resources come from the release that holds the query. Outputs and events bubble one level at a time, as today.
- **Editing nested modules:** the module editor's Add component offers Module (as the app editor does); inputs of an inner instance are props on it like any component's. Git deploys order modules so that one comes after the modules it holds (a topological order within the modules pass; a cycle in a commit is a deploy error naming the modules).
- **Multiplayer in the library query editor:** a collab document per library query draft (`library:<id>`) and per library query branch draft (now allowed by `services/collab/target.ts`), with `libraryQuerySpec` (M20) as its spec: the SQL (or REST fields) as `Y.Text`, parameters by name, the resource and timeout as values. The server materializes it into `library_queries.draft_definition` and folds other writes in, as for the other kinds (the draft revision trigger extended to `library_queries`). The editor moves onto `lib/collab-session.ts`: live edits, Monaco bound with others' cursors, its own undo, avatars in the header (no canvas, so no pointers), the connection state instead of CONFLICT; Run waits for `ensureSaved`.
- **The small gaps:**
  - **Renaming a module input** rewrites `inputs.<old>` reads everywhere in the module (templates, JS queries, transformers, outputs), with the property-read rewrite added to the rename tooling (`inputs` is a reserved built-in, so the read is unambiguous). Apps passing `input.<old>` aren't rewritten (they're other objects): the publish warning covers them.
  - **An instance on a page not shown** starts when its page is first shown (like the page's own queries), and then keeps its state when the page is left, as page-scoped values do.
  - **"Needs Use":** `resolveLibrary` and `resolveModule` say when an object exists but the person lacks Use on it, and the validator reports `no_use_access` ("You need use access to library query X") instead of `unknown_library` / `unknown_module`. Nothing more of the object is shown.
  - **The publish warning:** publishing a library query or module release that drops a parameter or input which apps, workflows or modules following it on `latest` pass lists them, with the names they pass, before publishing (a warning, not a refusal).
- **Tests:** property tests extended (a generated workflow with Library query blocks round-trips through Git, converges in collab and merges); the engine's library block against an in-memory provider (pinned, `latest` changing between retries, `current_user` per trigger, a child inheriting it); the server's vouching and draft rules; nested module validation (depth through `latest`, cycles, the publish check); the runtime with three levels and two instances; the library editor's collab document with two clients; Playwright for each part and the done-when; by hand on Docker Compose.
- **Not in M21:** library queries with JavaScript; a module's own pages; per-instance styling; version ranges; renaming a library query's or module's slug; following someone's view; library queries in Python code (blocks call them, code reads their data).
- **As built** (session 24, handoff §9p): as designed above, with these choices made while building: only the library query's schema, types, `libraryScope`, `LibraryInfo` and a new shared **`checkLibraryReference`** moved to `@ow/definition` (`validateLibraryQuery` stays in `@ow/app-definition`: it uses the app's names and stdlib); the block's parameters are string templates by name (like Function arguments), so the graph, rename, paste, the collab spec (`config.params.*` was already text) and the Git format needed no changes; the engine resolves the release on every attempt and takes the shorter of the block's and the library query's timeout; `current_user` is the run's `created_by`, now copied to child runs (manual runs already set it; webhooks, schedules and Pub/Sub don't). Nesting is computed in memory over every module release (`services/module-nesting.ts`), and the live-release check makes the draft the module's live release and checks every live module and live app's instances; the query path is an array of `{instance, releaseId}` (`apps.runQuery`'s `module`, `modules.runQuery`'s `path`; the M14 one-step form is gone). Git deploys needed no topological order: a deploy already retries in passes. The library editor got its own small store and session (`pages/library/store.ts`, `collab.ts`); the server's connector checks now come at publishing, as in the other editors. Renaming a module input needed property offsets from the identifier analysis (JavaScript only). "Needs Use": the resolvers return `{noUse: true}` (no id or name) instead of leaving the object out. The publish warning is a `publishImpact` query per kind, comparing the live release with the draft. Found while building: the module editor never synced the releases of instances it holds (modules couldn't hold any before). The done-when ran in Playwright and, by hand, on the user's Docker Compose stack (handoff §10).

## 2.25 Git sync's gaps (M22)

M11 (§2.13) put workflows and apps in Git, M14 library queries and modules, M20 merged branch drafts. What's left makes Git the way objects move between instances: the resources and config vars they depend on stay on each instance, a deploy that fails for a missing resource waits for someone to press Deploy now and nobody hears about it, folders aren't kept, and a few editor gaps remain.

- **Agreed with the user at the start of M22 (session 25):** resources and config vars are **protected and committed like workflows** (not edited in the repo only, not with branch drafts of their own); instances differ through **Git plus local overrides** of single non-secret fields; deploy problems are shown to admins as **a banner and sent to a workflow** named in Settings → Git; and all four small gaps come along: name, description and folder on branches, folders in Git, the branch list per object, renames followed in a merge. Deploys retry on their own.
- **The files:** `resources/<slug>/resource.json` — `{ name, description?, folder?, type, environments: { <env slug>: { config } } }`, `config` the connector's non-secret settings (its `configSchema`, checked by the server when deploying, since `@ow/git-format` stays pure); and `config-vars/<NAME>/config-var.json` (a directory, like every object: deploys and commits work by directory) — `{ description?, secret: boolean, values?: { <env slug>: string } }` (no values for a secret one). Secrets never go in: a key the connector's `secretsSchema` names in a config is a problem. The built-in database resource isn't kept. `ow.json` stays format 1 (directories it doesn't know are ignored by older instances).
- **Folders:** `folder` (`"Finance/Reports"`, names split on `/`, none empty) beside `name` and `description` in every object's JSON; not part of a definition's hash. A deploy creates missing folders of the object's kind and moves the object; on main a protected object's folder is read-only like its name.
- **Protecting a resource or config var** (Own; admins for config vars, which have no grants): as for workflows, its current settings committed onto `protect/<kind>-<slug>` and a pull request opened; protected at once. On main its non-secret settings, name, description, type and folder are read-only; **secrets** (per environment), **OAuth accounts**, **local overrides** and a secret config var's **values** stay the instance's. Unprotect (Own) leaves the files and stops deploying them (`not_protected`).
- **Save to branch:** the resource form (and the config var dialog) of a protected one, on main, keeps its edits in the browser and offers Save to branch: a new or existing branch, a message, the files that change with their diff (M11's Changes), then the commit (author = the person) and Open PR. No branch drafts for them: a commit is the edit. The branch moved and changed those files: CONFLICT (start again from the branch). Test connection works on the form's values as today.
- **Local overrides:** `resource_configs.overrides` (non-secret fields by path, e.g. `host`, `ssh.host`) applied over Git's `config` wherever a config is read (`toResolved`, Test connection, the form, the server identity rule); a deploy never touches them; the form marks overridden fields and lists them. A config var's value per environment can be marked **local** (`config_var_values.local`), which a deploy keeps. An environment in Git the instance doesn't have is skipped with a warning; an environment the instance has and Git doesn't keeps no config (the resource isn't configured there) unless overridden locally.
- **Deploying them:** first config vars, then resources, then library queries, modules, workflows and apps (each kind may name the ones before). A new resource is created protected without an owner (admins grant access), a config per environment, no secrets: it shows **"needs secrets in <environment>"** until an admin fills them in (queries there fail with that message). A changed one updates name, description, folder and each environment's `config`; secrets, OAuth accounts (whose consent hash may then ask to reconnect, as today), overrides and local values stay. A type change, a config the connector refuses, or a server identity the instance doesn't allow is a problem for that object (the rest still deploys). Audited as `resource.updated` / `config_var.updated` with `source: git`.
- **Retries:** a deploy's problem objects are re-checked, without a new commit, when a resource, config var, environment, library query or module is created or changed (a mark on `git_settings`, picked up by the next poll) and every `GIT_RETRY_MINUTES` (10; 0 off); one that now deploys does so as Deploy now would. Problems that only a commit can fix (a file that doesn't parse, an invalid definition) aren't retried.
- **Problems reach people:** `git.health` (admins) gives the last deploy's state and its problems; while there are any, admins see a banner at the top of the app (dismissable until the problems change) and a badge on Settings → Git. Settings → Git may name a **notify workflow**: when a deploy ends with a set of problems different from the last one, its live release is run (`created_by` null) with `{ deploy: { id, commit, url }, problems: [{ kind, slug, path, message }] }`, once; its own failure is logged, never retried into a loop. Recovering (no problems) runs it once more with `problems: []`.
- **Promotion:** instances share a repo and deploy different branches (Settings → Git's branch). Settings → Git's **Promote** opens (or returns) the pull request from this instance's deploy branch into another branch (`git.openPromotion`); what differs per instance stays in secrets, overrides and local values.
- **Editors:** a protected object's name, description and folder are edited on a branch (the workflow's Settings tab, the app's settings dialog, the library query and module editors) through `branchDrafts.save` and committed as meta; on main the app editor's inspectors are disabled, not just ignored. `git.branches({ kind, id })` lists the branches that change the object's directory against the deploy branch, or hold its open drafts, first (one `ls-tree` of the directory per branch, up to 100 branches); the branch picker groups them.
- **Renames in a merge:** before M20's merge, each side's renames against the base are found (an item gone and one new item equal to it once references to the old name are read as the new one; blocks, functions, queries, transformers, components, pages), and the rename is applied to the base and to the other side with the rename tooling (so the other side's edits and new references follow); then the merge runs as before. Both sides renaming one item to different names is a conflict over its name (pick one); a rename on one side and a delete on the other stays deleted-and-changed.
- **Tests:** property tests in `@ow/git-format` (resources, config vars and folders round-trip) and `@ow/collab` (a rename on one side and edits on the other merge to both); the server's protect, Save to branch, read-only rules, overrides, deploy order, needs-secrets, retries, health and notify against local bare repos and the fake GitHub API; Playwright for each part and the done-when with a second instance; by hand on Docker Compose.
- **Not in M22:** GitLab and other hosts' pull requests; a GitHub App; groups, permissions, environments, API keys and Git settings themselves in Git; resource branch drafts; deleting objects whose directory left the branch (still flagged `missing`); secrets from an outside secret manager.
- **As built** (sessions 25–27, handoff §9q): as designed above, with these choices made while building. **Format:** resources and config vars are their own `SettingsKind` in `@ow/git-format`, kept apart from `ObjectKind` (the kinds with drafts and releases); config vars have no folder; the package refuses a `secrets` key, and the server refuses secrets named inside a config when deploying. **Protecting:** built-in resources can't be; the branches are `protect/resource-<slug>` and `protect/config-var-<NAME>`; a resource needs Own in every environment it's seen in, config vars admins. On main a protected resource's `saveConfig` takes Git's config unchanged (compared canonically after the connector's parse) with new secrets only. **Overrides** are set with `resources.setOverrides` and edited in **one "Overrides on this instance" card** (a setting picked from the resource's fields, its value checked against Git's type), the user's choice in session 26, instead of a mark beside each field of every form; a config var's local value is "Save here only". **Save to branch** is one pair for both kinds, `git.settingsChanges` and `git.commitSettings` (default branch `settings/<kind>-<slug>`), sharing a dialog (`components/settings-git.tsx`). **Retries:** the mark is set from tRPC's `ctx.audit` for every audited `resource.*`, `config_var.*`, `library_query.*` and `module.*` action but query runs (environments have no API that changes them), so no router calls it itself; a retry that ends with the same problems records nothing. **Health and notify:** the notify workflow's live release runs in the default environment with trigger type `git` (a new run trigger type), the problem set stored before it runs; the banner is dismissed per problem set (in the browser's storage) and `git.health` is polled every 60 s. **Editors:** name, description and folder are set in **one Details dialog in the shared Git bar**, which all four editors use, instead of a form in each; `branchDrafts.setDetails` writes them without bumping the draft's revision (the shared document folds bumps in). **Renames** are found per kind by a `Renamer` in `@ow/collab` (workflows: blocks and functions; apps and modules: components, queries, transformers, variables and pages; library queries: none), and followed only when the base and both sides parse against the kind's schema (a broken file falls back to the plain merge); an item renamed **and** changed on the same side reads as deleted and added; the merge dialog says "renamed differently on each side". The done-when's spec starts **instances of its own** (a bare repo, a fake GitHub, two servers on their own databases), because a second instance deploying the shared e2e repo's main would get every other spec's objects. Found while building: a background `git gc` in the e2e's temporary clones made `rmSync` fail with ENOTEMPTY (`5703c84`); clearing Git settings or deleting a workflow leaves its row in the deploy state (handoff §13). The done-when ran in Playwright and, by hand, on the user's Docker Compose stack against a scratch GitHub repo (handoff §10).

## 2.26 Python's follow-ups (M23)

M12 (§2.14) runs each Python execution in a fresh jail: `import pandas` costs ~210 ms every time, what the code prints arrives when it ends, and the packages are the image's. M23 closes those three gaps without loosening the jail.

- **Agreed with the user at the start of M23 (session 28):** the warm pool is **pre-started, single-use jails** (isolation as today: nothing carries over between executions; not a reused interpreter, not a fork server); packages are **declared by each workflow** (pip requirements), installed by a **separate builder** with internet access, **wheels only**; the jail keeps no network.
- **Logs as they print:** `POST /run` with `"stream": true` answers `application/x-ndjson`, chunked: `{"log": {"level", "message"}}` per line as the code prints it (a partial line goes out after 250 ms without a newline; the 1 MB cap as before, then one `warn` line), then `{"outcome": {ok, result | error}}` as the last line. Without `stream` the answer is as before. `PythonExecutorClient.run` streams and calls `onLog` per line, so the lines reach `work.log` and the run's logs (the store flushes every `LOG_FLUSH_MS`) while the block runs, and the run view shows them live as it does JavaScript's. A timeout or cancel keeps the lines already sent; a stream that breaks before its outcome (the executor died) is `unavailable`, with the lines so far.
- **The warm pool:** the executor keeps `PYTHON_WARM_JAILS` (default `PYTHON_MAX_CONCURRENT`) jails started ahead: nsjail and the interpreter running `runner.py --warm`, which imports `PYTHON_PREIMPORT` (default `numpy,pandas`; empty for none) and then blocks reading its request on stdin. A `/run` for a workflow without packages takes one (or starts a cold one, as today, when none is ready), and a replacement starts in the background; each jail runs one execution and exits. Limits that counted from a jail's start now count from its request: the server's deadline (the block's timeout) as today; the CPU limit set by the runner itself once the request arrives (`setrlimit(RLIMIT_CPU)` to what it has used plus the timeout rounded up plus one: a process may lower its own limit); nsjail's `--time_limit` becomes the idle limit plus the longest timeout, a backstop only; a warm jail idle for `PYTHON_WARM_MAX_IDLE_SECONDS` (600) is replaced. The pre-import's memory counts towards the jail's 256 MB (measured in step 2; the default may rise) and the container's `mem_limit` must hold the running and the warm jails. Warm jails take no run or check slot. The pre-imported modules are in `sys.modules` even when the code doesn't import them, which is harmless (`to_json` already looks there). `/health` reports the pool (ready, starting, served warm and cold); each execution's log line says `warm`. Target: a block that imports pandas answers in under 60 ms p50 over HTTP (today ~250 ms).
- **Workflow packages:** `settings.python.requirements` (stored sparsely): up to 30 PEP 508 requirements, a name with extras and version specifiers only (`polars==1.9.0`, `openpyxl>=3.1`); refused: URLs, paths, `-e`, `--index-url` and every other option, environment markers. Edited in the workflow's Settings ("Python packages", one per line) by anyone with Edit; in Git as `requirements.txt` beside the workflow's JSON. Each workflow, a child workflow included, has its own; its functions share it. A workflow without requirements runs exactly as today.
- **The builder** (`python-builder`: a second target of `apps/code-executor`'s Dockerfile, the same base image, so the same Python and platform, plus pinned pip): `POST /build {requirements}` resolves them (`pip install --dry-run --report`, `--only-binary :all:` so no package's code runs while installing; the index `PYTHON_PACKAGE_INDEX_URL`, PyPI by default, or a proxy) into a **lock** (each package, its version and wheel hash, and the platform), then installs exactly the lock (`--require-hashes --no-deps --target`) into `envs/<lock hash>/` on a shared volume, atomically (a temporary directory renamed): `{ lock, envId, sizeBytes, log }` or `{ error, log }`. `POST /install {lock}` installs a known lock without resolving (a release's, after the env was removed or on another instance); a lock from another platform resolves the same versions again. Limits: 5 minutes per build, `PYTHON_ENV_MAX_MB` (1024) per env, `PYTHON_MAX_BUILDS` (2) at once and one per lock; envs unused for `PYTHON_ENV_KEEP_DAYS` (30) are removed (their locks rebuild them). Its own token (`PYTHON_BUILDER_TOKEN`), no other secrets, no database; it alone has internet access (in Compose: the `executor` network and an egress network); the executor stays on the internal network and only reads the volume.
- **Runs:** the server keeps `python_envs` (migration 0032: the requirements' hash and platform → lock, env id, size, state, the last build's log, last used) and asks the builder before running a workflow with requirements. A draft run resolves when the requirements changed since the last lock, else reuses it; publishing, rollback and Git deploys build the env and keep the **lock in the release** (a failed build refuses the publish with the build's log, like a syntax error), so live runs use exactly what was published. The run request names the env (`envId`); the executor bind-mounts `envs/<envId>` read-only into a cold jail (a warm jail can't take it: mounts are fixed when a jail starts; a warm pool per env may come later) and the runner puts it first on `sys.path`, so its versions win over the image's (a different pandas works) and the image's packages stay available for what it lacks. An env missing on the volume is installed from the lock before the block runs. Failures are `python_packages` errors with the build's log in their details; without a builder (`PYTHON_BUILDER_URL` unset) a workflow with requirements fails `python_packages_unavailable`, and the Settings field says so.
- **Safety:** a package's code runs only in the jail: no network, no secrets, only the scope the block gets anyway, so a malicious package can do what the block's own code can (return wrong data), not send anything anywhere. Installing runs no package code (wheels only). Requirements are part of the definition (history, releases, Git, audit of saves); each build is audited (`python.env_built`, with the lock's packages) and logged.
- **The editor:** the workflow's Settings → Python packages: the field with the validator's problems per line, the env's state (resolving, installed with its packages and size, failed with the log) and Install now. Completions stay as they are (no introspection of packages).
- **Ops:** Compose's `code-executor` mounts the envs volume read-only, `python-builder` read-write with egress; `.env` gains `PYTHON_BUILDER_TOKEN` and `PYTHON_PACKAGE_INDEX_URL`; tests start the builder like the executor (`startTestBuilder`, beside `startTestExecutor`) with a local package index serving a wheel the test builds; the runbook (`docs/runbooks/python.md`) gains the pool, the builder, a proxy index and cleaning envs; metrics: warm and cold executions, builds and their duration.
- **Done when:** a block that imports pandas answers in under 60 ms p50 over HTTP from the warm pool, and no state carries over between two executions (a module attribute set, a file in `/tmp`); a block printing a line a second shows the lines in the run view while it runs; a workflow declaring a package the image lacks imports it in a draft run and, published, in a live run, while another workflow gets `ModuleNotFoundError`. In Playwright against a local package index; on Compose against PyPI (`polars`).
- **Not in M23:** network from the jail; Python in apps; a warm pool per env; packages from source (sdists); private indexes with credentials (later, through a secret config var); allow and deny lists of packages; passing the scope without a JSON copy.
- **As built** (session 28, handoff §9r): as designed above, with these choices made while building. **Streaming:** the executor keeps the lines as they come (a partial line per level; another level's output ends it, as before) and hands each read's new lines to the stream; the cut-off line goes out when the cap is hit; a failed write is a hang-up. **The pool:** a `Jail` is started apart from its request (a warm one gets `OW_WARM`, its result fd, and `OW_PREIMPORT`), says it's ready with one byte on the result pipe, and the runner sets its own CPU limit from the request (never above the hard limit nsjail set). Measuring showed warm runs **slower** than cold at first: the interpreter's teardown with pandas loaded, which the server waits for, so the runner **`os._exit`s after its outcome**. Two jails starting at once slowed back-to-back small blocks (a Python loop) by ~15%, so they start **one at a time** (`PYTHON_WARM_START_PARALLEL`, 1). A warm jail holds ~42 MB, so `PYTHON_MEMORY_MB` stays 256. Measured on Compose: pandas p50 32 ms warm (target 60), trivial 20 ms. **Requirements:** the schema is loose (100 strings of 1000) and the validator says what's wrong with each line, so one doesn't hide the rest; `requirements.txt` read back drops blank and comment lines; the collab spec has no rule for them (strings by position). **The builder** checks requirements again, resolves with `pip install --dry-run --ignore-installed --only-binary :all: --report`, and takes up to 500 (a lock pinned again for another platform); envs are `envs/<envId>/site` with `lock.json` and a `used` file touched by every build or install (what the hourly cleaning reads). It's a stage of the executor's Dockerfile (pip 26.2.1 by hash). **Runs:** the engine gets a `PythonEnvProvider`; a run asks for its env **as it starts** (only with requirements and Python fields), shared by its blocks (`shared`: one call, a failure not kept), and a Python block waiting over a second logs so — the block's timeout still applies, since the orchestrator's race reports it first. `python_envs` keys a set of requirements by its sorted hash; a ready row's lock is installed again (which touches the env and brings it back if removed), only a `platform` failure resolves anew. **Releases:** `checkReleasable` works out the lock last (after every cheaper refusal), **reusing the draft runs' lock**; rollback installs the release's own lock and fills one in for a release without. No builder: `python_packages_unavailable` from `pythonDiagnostics` (a new code), so runs and publishing refuse. **The editor:** `workflows.pythonEnv` (state for the field's requirements, saved or not) and `workflows.installPythonEnv`, the state under the field 600 ms after it settles. **Compose:** `python-builder` (no privileges, `mem_limit` 1g, the `executor` network and `builder-egress`), the `python-envs` volume (read-only in the executor, which starts after the builder so the volume takes its owner). Found while building: clearing the run timeout dropped every workflow setting (fixed with `withSetting`); a server test read releases without `ORDER BY` and broke when the new column made Postgres use the newest-first index. The done-when ran in Playwright against a local package index and, by hand, on the user's Docker Compose stack against PyPI (`polars==2.0.0`; handoff §10). **The review** (handoff §9r) changed: installs of an env that's there take no build slot and a build's time counts from its slot; a warm jail's memory limit is raised by its imports; a stream's writes time out (10 s); a release's lock from another platform is installed with its versions pinned on rollback too; a run's early install failure isn't built again by its block.

## 2.27 The app builder's gaps (M24)

M8 and M10 (§2.11) built apps; M13 to M16 and M21 gave the editor undo, modules and multiplayer. What's left in the app builder (handoff §13 "Apps") is what people notice building a real app: a Table that can't filter, compute or add rows, one selected component at a time, no way to drag a component into a container, no navigation bar, plain boxes as containers, and releases you can't compare. M24 closes those.

- **Agreed with the user at the start of M24 (session 29):** the scope is **Table upgrades**, the **editor canvas** (several components selected, dragging between containers), a **release diff view**, **charts and pages polish** (time axes, page renames, real links, a confirm dialog, nested folders), an **app frame** (a header bar and a sidebar) with **richer Navigation**, and **Containers** with views (tabs), folding, scrolling and styling. Not in M24: a mobile layout, custom components (each a milestone of its own); AI actions stay last.
- **No schema bump** (as M10's pages): every addition is an optional field, so an app from before M24 means exactly what it did. New on a component: **`slot`**, where it sits in its parent: for a global component, the frame's `header` (the default) or `sidebar`; inside a container, one of its views by name, or its `header` or `footer`. New on the definition: **`frame`** (below). The validator refuses a slot its parent doesn't have; the collab spec, the merge and Git sync carry the new fields as values (no new identity arrays besides those below); `@ow/git-format` needs nothing new (they stay in the app's JSON).
- **Table: columns.** The inspector edits `columns` as a **list** (add, remove, drag to reorder; per column its key, label, type, editable, hidden, width, a computed value, filtering on or off), with "Edit as JSON" kept. A **computed column** is a column whose `value` is a template reading **`currentRow`** (and `i`, the row's index, plus the app's scope): `{{ currentRow.qty * currentRow.price }}`. Its `value` isn't evaluated with the `columns` prop: the graph gives each table one more node (its rows with the computed values), depending on `data` and on what the templates read, evaluated in the app's Worker one row at a time with one compiled function per column (the watchdog as for any code). A computed key can be new or replace a key of `data` for display; computed cells aren't editable. What the table shows, sorts, searches and filters are the computed rows.
- **Table: filters.** With `filters` on (a prop), each column's header has a filter menu by its type: text (contains, equals, is empty), number (=, ≠, <, ≤, >, ≥, between), boolean, date and datetime (before, after, between); filters combine with AND. State **`filters`** (`[{ column, op, value }]`), methods `setFilters(filters)` and `clearFilters()`, event `filterChange` (back to the first page). With `scroll` and `pages` the table filters its rows itself (after computing); with **`server`** it doesn't: the query reads `table1.filters` through a new SQL helper, **`{{ sql.where(table1.filters, ['name', 'city', 'total']) }}`**, which becomes a parameterized condition (columns checked against the list written in the query, as `sql.column` does; values bound, never SQL text; `TRUE` when there are none) in Postgres, MySQL and BigQuery.
- **Table: resizing and new rows.** A header's right edge drags to resize: in the editor it saves the column's `width` (listing the columns first when they were inferred); in a running app it lasts until the page reloads. With **`allowAddRow`**, an Add row button opens an empty editable row at the top (its editable columns); state **`newRows`** holds rows added and not saved yet, each removable; `saveChanges` fires `save` with `changesetArray` and `newRows` both, then clears them; `clearChangeset` clears both; event `addRow`.
- **Containers.** A Container gains **views**: `views` (`[{ name, label? }]`, an identity array by name; none is today's single grid), shown as tabs (`showTabs`, else switched by code only), state **`currentView`** from `defaultView`, methods `setView(view)`, `nextView()`, `previousView()` (for steps), event `viewChange`. Each child of a container with views is in one view (its `slot`; one without a slot, or naming a view that's gone, shows in the first). Only the shown view's children render; the others keep their values (an input in a hidden view still has what was typed). Renaming a view rewrites its children's slots and `setView('…')` strings as page renames do (below); deleting a view asks where its children go. **Folding:** `collapsible` and `defaultExpanded`, state `expanded`, methods `expand()`, `collapse()`, `toggle()`, events `expand` and `collapse`; folded, the container is its header's height and what's below it on the grid moves up (in a running app; the editor shows it unfolded, with a folded marker). **Scrolling and styling:** with `scroll` (on for new containers) the content scrolls inside the container's height instead of overflowing; `background` (none, surface, canvas, accent, or a color template) and `padding` (none, small, medium, large), from the theme's tokens so dark mode works; a **header** slot (beside the title and tabs) and a **footer** slot (below the content, for buttons), each a one-row grid.
- **The app frame.** `frame` on the definition (Settings → Layout in the app editor): a **header** bar fixed at the top (`frame.header`), a **sidebar** at the left (`frame.sidebar`: narrow, medium or wide), or both; pages scroll beneath and beside them. Global components sit in the header (the default slot) or the sidebar (`slot: 'sidebar'`); without a frame, global components render above each page as today. Built-in options: the app's name in the header (`frame.showTitle`) and the signed-in user with a menu (`frame.showUser`). On a narrow screen the sidebar folds behind a menu button.
- **Navigation.** Items become `{ page?, params?, url?, label?, icon?, hidden?, items? }`: a page (with URL params) or an outside URL (opens in a new tab), an icon from a fixed set (lucide's, a curated list, so the bundle stays small), `hidden` a template, and `items`: one level of sub-links (a dropdown when horizontal, a group when vertical, open while one of its pages is shown). Links are **real `<a>` elements** with the page's URL, so opening in a new tab and copying a link work; a plain click still opens the page in place, as `utils.openPage` does. The inspector edits the items as a list (like the columns), "Edit as JSON" kept. Empty `items` links every page by title, as today.
- **Several components selected.** The editor's selection becomes a list: shift- or cmd-click on the canvas and in the tree adds and removes, Escape clears, cmd+A selects the page's components. With several selected, the inspector shows how many and what applies to all (delete, duplicate, copy, move into a container); M13's keys and clipboard act on all of them (with what's inside them); dragging one moves those on the same grid by the same offset, and the arrow keys nudge by one cell, each one undo step. Presence already sends a list (M16).
- **Dragging between containers.** A component's drag handle can be dropped on any other grid: the page, a container's view, header or footer, a form, an open modal, the frame's header or sidebar. The target grid lights up; the drop changes `parent`, `slot`, `page` and the position in one edit (its children come along; a multi-selection moves together). Refused: into itself or its own children, a modal anywhere, a form into a form. The inspector's "Inside" field stays (for the keyboard).
- **Release diff.** `@ow/collab` gains **`diff(before, after, spec)`**, the two-way companion of M20's merge, driven by the same spec: items of identity arrays added, removed, renamed (M22's rename detection) or changed; values changed by path; text (code, SQL) as line hunks. The Releases panel of the four editors (workflows, apps, modules, library queries) gets **Compare**: a release against the one before it, the live one, or the draft. A dialog lists the changes grouped by kind (components, queries, blocks, settings…), each expanding to its field changes and a line diff of its code. Apps, modules and library queries gain a `release` query returning one release's definition (workflows have `releases.get`).
- **Charts.** An x key of dates or datetimes gets a **time axis** (`xAxis`: auto, category or time): points placed by time, gaps kept, ticks by day, week, month or year in the viewer's locale, through Chart.js's time scale with a small date adapter of our own (on `Intl` and UTC dates, no new dependency, unless it grows past ~150 lines; then `chartjs-adapter-date-fns`). Charts already follow the theme (Optiply UI); §13's "light mode only" is stale.
- **Pages.** Renaming a page rewrites `utils.openPage('old', …)` in JS queries, transformers, scripts and templates (a string literal as the first argument; a computed name isn't followed), the way entity renames rewrite references (`rename.ts`).
- **A confirm dialog.** `useConfirm()` on the existing `Dialog` (a title, the message, a danger button for destructive actions, Enter and Escape) replaces the web app's 22 `confirm()` calls (deletes, rollback, revoke, close a branch draft, unprotect, the clipboard's untrusted paste, switching with unsaved changes).
- **Nested folders.** The workflow, app, module and library query lists show folders as a tree: breadcrumbs, a folder's subfolders first, a subfolder created inside the one open, folders renamed and moved (refused into themselves). The API has `parentId` since M10; renaming and moving are added where missing.
- **Done when:** in Playwright, (1) a client-side table with a computed column and two filters shows the right rows, and a server-paged table over 10k rows filters through `sql.where`; resizing a column in the editor saves its width; two added rows reach an insert query through `newRows`; (2) three components selected and dragged together, one dragged into a container's second view, and undoing all of it returns the exact starting definition; (3) a container with two tabs switched by a button's `setView`, folded and unfolded, the component below moving up; (4) an app with a header and a sidebar holding a Navigation with an icon, a group and an outside URL, whose page link opens that page from its URL in a new tab; (5) publish, move a component and change a query's SQL, then Compare the release with the draft shows both, the SQL as a line diff; (6) a chart of a month of daily rows with a gap draws a time axis; renaming a page rewrites `utils.openPage('orders')`; deleting a folder asks in the dialog. On Compose, by hand.
- **Not in M24:** a mobile layout; custom components; themes per app; per-page access; column templates other than the value (cell colors, per-row editability); undo that outlives a reload.
- **As built** (sessions 29–30, handoff §9s): as designed above, with these choices made while building. **Table:** a computed column's `value` is a field of a per-table node **`<table>.$rows`** with the locals `currentRow` and `i` (so the validator, renames, the graph and paste honour them), evaluated in the Worker; the filters prop is **`showFilters`** (the state is `filters`); one filter per column from the header (code sets more); `sql.where(filters, ['a', …])` takes the columns as a literal list (checked like `sql.column`'s), binds every value, uses no `LIKE` (`%` and `_` are characters), and makes the plan renumber its placeholders per dialect; a set `width` is now the column's exact width (it was a minimum). **Slots:** `slotOf` decides where a component sits (a container's first view when it names none or one that's gone; the sidebar only for a component on every page in an app with one, so nothing vanishes when the sidebar goes); renaming a view rewrites slots, `defaultView` and `setView('…')` in code through `rewriteCallArgs`, which page renames use for `utils.openPage('…')` too. **Containers** scroll by default (content that overflowed now scrolls inside). The frame's settings are the editor's **Frame** section under Pages rather than Settings → Layout. **Navigation's icons** are 38 curated lucide names. **The canvas:** the selection is a list beside the inspector's component; since the editor's grid compacts upward, moving several (a group drag, the arrow keys) goes through react-grid-layout's own `moveElement` and compactor, and every grid takes drops (the palette's too) through a move grip's HTML5 drag, refused by `moveIntoReason`. **The diff** is `diff(spec, before, after, { renamer })` in `@ow/collab`; Compare is a dialog per editor (Escape back to the releases), with `apps.release`, `modules.release` and `libraryQueries.release`. **Charts:** no date adapter at all: a time axis is Chart.js's linear scale over milliseconds with our own ticks and labels (`chart-model.ts`), for line and area charts. **The confirm dialog** is a function, `confirmDialog(…)`, with one `ConfirmHost` (not a hook, so non-component code can ask); every `window.confirm` is gone. **Folders** are browsed one at a time (`?folder=`: the path, subfolders first, then what's in it) rather than shown as one tree; `folders.move` locks the kind's folders to refuse loops; a folder holding folders can't be deleted. Found while building: the fake Pub/Sub delivered to pulls whose caller had hung up (the M19 flake, `2801e8d`); the component tree missed components outside a container's first view; and in the Compose check, a component moved to another page vanished from the editor (it now opens that page). The done-when ran in Playwright and, by hand, on the user's Docker Compose stack (handoff §10).

## 2.28 Custom components (M25)

Apps (§2.11, §2.27) have about thirty built-in components; anything else (a Gantt chart, a map, a signature pad, a vendor's widget) can't be built today. Retool's answer is custom component libraries: React code built with a CLI and run in a sandboxed iframe that talks to the app through `Retool.useStateX` hooks (Part 1). M25 builds that, with the code written and built inside the platform.

- **Agreed with the user at the start of M25 (session 31):** custom components live in a **new object kind, the component library** (several components per library, built like M14's modules: drafts, semver releases, grants, folders, Git sync; apps reference a release, pinned or `latest`). Code is **written in the browser** (Monaco: TSX, JSX, TS, JS and CSS files) and **built on the server** with esbuild, React supplied by the host; an **upload API** takes a prebuilt bundle too, so a CLI can push one later. A library **declares npm dependencies**, locked at a build and kept by the release (like M23's Python packages); a component's **network access is blocked** by a Content Security Policy except for the origins its library lists, which **only admins** set.
- **A new object kind, built like modules:** `component_libraries` (slug, name, description, folder, `draft_definition`, `draft_revision`, `live_release_id`, `git_protected`) and `component_library_releases` (semver, the canonical definition and its hash, notes, `git_commit`, `created_by`, plus the build: the lock, the bundle's JS and CSS, their hash and size). `component_library` joins `PERMISSION_OBJECT_TYPES`, `FOLDER_OBJECT_TYPES` and `GIT_OBJECT_KINDS` (a column in `git_branch_drafts`), `canCreateComponentLibraries`, audit `component_library.*` as for modules, plus `component_library.origins_changed`. Use lets someone use a library's components in an app or module; Edit opens its editor and builds its draft; Own deletes it and manages grants; a viewer of an app needs nothing on the libraries it uses. Deleting a library that an app's or module's draft or live release uses is refused (`usedBy`); publishing one that apps follow on `latest` lists them first and warns when a component or prop they use is gone.
- **The definition** (`packages/app-definition/src/component-library.ts`): `{ schemaVersion: 1, files: [{ path, content }], dependencies: { <npm name>: <range> }, allowedOrigins: [<https origin>], components: [{ name, label, description?, entry, props: { <name>: PropSpec }, state: { <name>: { default } }, events: [<name>], methods: { <name>: { params } }, defaultSize: { w, h } }] }`. `entry` is a file whose default export is the React component. The interface is **declared**, not inferred from the code, because the validator, the graph, the inspector and the completions need it without running anything; the component reads it through the SDK. The validator: paths (relative, no `..`, known extensions, ≤ 2 MB of source), component, prop, state, event and method names (identifiers; `library`, `version` and `component` reserved), prop types and defaults (the registry's `PropType`), an `entry` that exists, npm names and ranges (`invalid_dependency`), origins (`https://host[:port]`, no paths or wildcards but a leading `*.`; `http://localhost` allowed).
- **The SDK** (`packages/component-sdk`, imported as `@ow/component-sdk` in a component): `useProp(name)` (the prop's evaluated value), `useStateValue(name)` returning `[value, set]` (the value shows in the app as `custom1.<name>`), `useEvent(name)` returning a function that fires the component's event (its handlers run in the app), `useMethod(name, fn)` (the app calls `custom1.<name>(…)`; a returned value or promise answers the caller, 10 s at most), `useTheme()` (the Optiply tokens and light or dark, also as CSS variables `--ow-*` on the frame's root), and `utils` (`openUrl`, `openPage`, `notify`) going through the app. Types for the SDK and React are given to Monaco; npm packages' types aren't (they're `any`).
- **The build** (`apps/server/src/services/components/build.ts`, in the worker): the files are written to a temporary directory with a `package.json` of the declared dependencies; `npm install --ignore-scripts --no-audit --no-fund` (the registry from `NPM_REGISTRY_URL`, default the public one; no install scripts ever run) makes or follows the `package-lock.json`; esbuild bundles each component's entry (TSX, JSX, CSS imports, assets inlined up to a size) into one ESM file and one CSS file, `react`, `react-dom` and `@ow/component-sdk` mapped to the frame's globals so there's one React. Limits: 120 s, 200 MB of installed packages, a 5 MB bundle; errors come back with file, line and column for the editor's markers. Builds are cached by the hash of the files, the dependencies and the lock (a `component_bundles` table, any API process serves them); a draft build keeps its lock in the draft; **publishing builds the draft, then stores the lock and the bundle on the release**, so a release never changes. The upload API (`componentLibraries.uploadBuild`: a bundle, its CSS and a manifest) makes a release from a prebuilt bundle; that release has no files and is marked "uploaded".
- **The frame at run time:** a custom component renders as an `<iframe sandbox="allow-scripts">` (no `allow-same-origin`: an opaque origin, so it reads neither the platform's cookies nor the parent's DOM) whose `srcdoc` holds a `<meta>` CSP: `default-src 'none'`, scripts only from the bundle's URL and the frame runtime's, styles from the bundle's CSS and inline, `img-src`, `font-src`, `media-src` and `connect-src` from `data:`, `blob:` and the library's `allowedOrigins`. The **frame runtime** (React, ReactDOM and the SDK's inside, built by the web app as a separate entry, cached by its hash) loads the release's bundle (`/api/component-bundles/<hash>.js`, immutable) and mounts the component. Host and frame talk over a `MessageChannel` handed over once: props in (each change), state, events and method calls out and in, theme changes in, method results, errors (a component that throws shows the error in its box, like a failing query). A frame that doesn't answer in 10 s shows "not responding".
- **In an app or module:** a component of type **`custom`** with `props.library`, `props.version` (`latest` or a release), `props.component`, and a template per declared prop (`props['prop.<name>']`, as a module's `input.<name>`); `customComponentSpec(manifest)` builds its registry spec (declared props as props, declared state as state, events, methods), so the validator, the graph, renames, paste, the inspector and the completions treat it like a built-in, and an instance whose release isn't known yet has an open spec (as M14's modules). The app's runtime keeps the state the frame sets (`custom1.selected`), fires its events' handlers and sends method calls to the frame. `apps.open` returns the resolved release of each library used (manifest and bundle hash, not the files), as for modules; publishing needs Use on each and a live release for `latest` (`unknown_component_library`, `unknown_custom_component`, `unpublished`, `unknown_version`).
- **The library editor** (`/component-libraries/<slug>/edit`, the lists like modules': folders, grants, Used by): a file tree and Monaco (TypeScript's checking for the SDK's and React's types, the build's errors as markers), the **Components** panel (name, label, entry, props with types and test values, state, events, methods, default size), **Dependencies** (name and range; the lock's resolved versions after a build), **Allowed origins** (read-only unless admin), **Build** and a **Preview** of each component with its test props (the events and state it sets listed live), releases with M24's **Compare** (file hunks, manifest changes), multiplayer through M16's collab (a `componentLibrarySpec`: files by path as text, components by name), Git branch drafts and M20's merge. In the app editor: **Add component → Custom** (a library, a component, a version), the declared props in the inspector with `fx`, Open in library.
- **Git** (`@ow/git-format`): `component-libraries/<slug>/` with `library.json` (name, description, components, allowed origins), `package.json` (the dependencies), `package-lock.json` (from the release) and the files under `src/`. A deploy goes component libraries, library queries, modules, workflows, then apps; a deploy builds each changed library (an uploaded release can't come from Git). `allowedOrigins` changed through Git is trusted as any deploy is (protection decides who merges); the deploy audits `component_library.origins_changed`.
- **Done when:** in Playwright, (1) a library whose component imports a package from a test npm registry (served in the test, like M23's test index) and declares a prop, a state, an event and a method builds, previews and publishes 1.0.0; (2) in an app, the component's prop follows a query, a click inside the frame sets `custom1.selected` (shown by a Text) and fires an event whose handler runs a query, and a button calls `custom1.highlight(2)` whose result comes back; (3) a `fetch` to an origin not allowed is blocked (the component shows the error) and works once an admin adds the origin and the library is republished; the frame reading `parent.document` or `document.cookie` gets nothing; (4) publishing 1.1.0 that drops a prop warns about the app on `latest`, Compare shows the files' hunks, and the library round-trips through Git sync (a deploy rebuilds it); a module using the component works in an app. Then the Compose stack: the build in the image (npm and esbuild present), a cache volume, a real package from the public registry.
- **As built** (session 31, handoff §9t): as designed above, with these choices made while building. **Props:** a custom component's declared props are its props by their own names (`props.label`, like a module's inputs), not `prop.<name>`; `library`, `version`, `component` and `hidden` are reserved. **Origins:** anyone with Edit may change the draft's `allowedOrigins` (multiplayer edits arrive without a person to check), and **publishing a release whose origins differ from the live one's needs an admin** (Git deploys are trusted; both audited as `component_library.origins_changed`). **Builds run in the API process** that gets the request (Build, Publish, the deploying process), two at a time, not in the worker. **Bundles** are one ESM file exporting every component by name plus one CSS file, served to anyone signed in by hash; the page fetches them and hands them to the frame as text, which imports the bundle from a `blob:` URL (the CSP allows inline and `blob:` scripts only). **The lock isn't written to Git:** releases keep theirs and a Git deploy starts from the live release's lock (`package-lock.json` in the codec stays readable). Also: a frame that navigates itself is removed and reported (a CSP can't stop that request); in the app editor a cover over the frame lets a click select the component (a double-click lets it be used); bundles no release keeps go after 7 days (retention). Runbook: `docs/runbooks/components.md`. The done-when ran in Playwright (`m25-done-when.spec.ts`).
- **Not in M25:** a CLI (the upload API is there for one); private npm registries with credentials; npm packages' types in the editor; components that grow with their content (a frame keeps its grid size and scrolls); custom components as containers; inline components in an app's own definition; server-side rendering; per-app overrides of `allowedOrigins`.

## 2.29 SQS and Kafka triggers (M26)

M19 (§2.22) lets Google Cloud Pub/Sub messages start workflows, and said SQS and Kafka would come later as more kinds of the same trigger. M26 adds them: **Amazon SQS** (a queue with a visibility timeout, the closest to Pub/Sub) and **Apache Kafka** (a log with consumer groups and committed offsets, which has no per-message ack, nack or redelivery, so retries and dead letters are ours). Each comes with a resource that triggers name and that workflows and apps can send through.

- **Agreed with the user at the start of M26 (session 32, 2026-10-30):** both SQS and Kafka; a Kafka message whose run fails is **retried** (new runs with backoff, up to `maxAttempts`) and then **sent to a dead-letter topic** if the trigger names one, after which its partition moves on; Kafka messages run **in order per key** (one key's messages one at a time, in offset order; different keys, and messages without a key, in parallel up to `maxInFlight`); the Kafka resource connects **plaintext, SASL PLAIN or SCRAM over TLS, with mTLS client certificates, or with AWS MSK IAM**; the AWS identity (SQS and MSK IAM) is **an access key, a role assumed through STS, or the server's own AWS credentials** (opted into by the instance, chosen by admins only, M18's rule).
- **One consumer, three kinds** (`packages/engine/src/queue-consumer.ts`): M19's `pubsub-consumer.ts` is split into what every kind shares (the lease per trigger, restarting a subscriber when its release, environment or settings change, `startDelivery` and the duplicate rules, the hold loop polling run statuses, `maxInFlight`, `maxHoldMinutes`, the trigger's state on `workflow_triggers.state`, `stop()` handing held messages back) and an **adapter per kind** (`pull(max)`, `extend(held)`, `settle(message, outcome)`, `close()`): Pub/Sub's is today's code, unchanged in behaviour (M19's tests and done-when are the guard). `pubsub_deliveries` becomes `queue_deliveries` (same columns; the message id is Pub/Sub's id, SQS's `MessageId`, or Kafka's `<topic>/<partition>/<offset>@<timestamp>`, the timestamp so a topic made again isn't taken for the old one). Metrics gain a `kind` label: `ow_queue_messages_total{kind,outcome}`, `ow_queue_in_flight{kind}`, `ow_queue_pull_errors_total{kind}` (Pub/Sub's `ow_pubsub_*` names go; the runbook says so).
- **The AWS identity** (`packages/connectors/src/aws/`): `@aws-sdk/credential-providers`: an access key id and secret access key (the secret stored encrypted), **or the server's own credentials** (`fromNodeProviderChain`: environment, `~/.aws` files, SSO, web identity, ECS and EC2 metadata; off unless `AWS_SERVER_IDENTITY=allow`; only admins may save a resource that uses it, M18's rule generalised to `aws:<region>`), optionally followed by **assuming a role** (`fromTemporaryCredentials`: a role ARN, an optional external id, session name `ow-<resource>`), all per region. Shared by SQS and MSK IAM. Test connection names the identity (STS `GetCallerIdentity`). `configureAws` sets fake endpoints for tests, like `configureGoogle`.
- **The SQS resource** (type `sqs`, `@aws-sdk/client-sqs`): config `{region, identity: 'key' | 'server', accessKeyId?, roleArn?, externalId?, endpoint?}` (an endpoint override for LocalStack, ElasticMQ and the fake; admins only), secret `secretAccessKey`. Test connection: the identity, then `ListQueues` (a 403 still passes, as Pub/Sub's topic listing does: receiving needs only the queue). Query **send** `{queue (URL or name), messages}`, with `messages` JSON with `{{ }}` (`[{body, attributes?, groupId?, deduplicationId?, delaySeconds?}]`), sent with `SendMessageBatch` in tens, answered with the message ids.
- **The SQS trigger** (`triggers.sqs`, up to 20): `{name, enabled, resource, queue (URL or name), environment?, maxInFlight (1–100, default 4), maxHoldMinutes (default 60, at most 720: SQS's 12 h visibility limit)}`. The adapter long-polls `ReceiveMessage` (20 s, up to 10 at a time, all attributes), holds a message by `ChangeMessageVisibility` (60 s, renewed every 20 s, as Pub/Sub's deadline), **deletes it when its run succeeds** and sets its visibility to 0 when it fails or is cancelled, so the queue's redrive policy (`maxReceiveCount`, a dead-letter queue) applies. FIFO queues need no work of ours: SQS hands out a message group's next message only after the one before is deleted. A run's input: `startTrigger.data` the body (parsed as JSON when it is JSON, else text), `startTrigger.message` `{messageId, queue, attributes, messageAttributes, receiveCount, sentAt, groupId?, deduplicationId?}`. Run trigger type `sqs`.
- **The Kafka resource** (type `kafka`): config `{brokers, auth: 'none' | 'plain' | 'scram-sha-256' | 'scram-sha-512' | 'mtls' | 'aws-msk-iam', tls, username?, caCertificate?, clientCertificate?, clientId?}` plus, for MSK IAM, the AWS identity fields above; secrets `password` and `clientKey`. The client is **`@confluentinc/kafka-javascript`** (Confluent's supported client on librdkafka, with a KafkaJS-style API) unless step 3a's spike finds it won't install in the image or misbehaves, in which case `kafkajs` (pure JavaScript, no release since 2023); MSK IAM is SASL OAUTHBEARER with a token that is a SigV4-presigned `kafka-cluster:Connect` URL, refreshed before it expires. Test connection: connects, lists the brokers and counts the topics, each failure named (`connection`, `auth`, `tls`). Query **produce** `{topic, messages}` (`[{key?, value, headers?, partition?}]`, JSON with `{{ }}`), answered with each message's partition and offset. No SSH tunnels (brokers advertise their own addresses).
- **The Kafka trigger** (`triggers.kafka`, up to 20): `{name, enabled, resource, topics (1–10), groupId (default `ow-<workflow>-<trigger>`), startAt ('latest' | 'earliest', for a group with no offsets yet), environment?, maxInFlight (1–100, default 4), maxAttempts (1–20, default 3), retryBackoffSeconds (default 10, doubling, at most 15 min), deadLetterTopic?, maxHoldMinutes (default 60)}`. The worker holding the trigger's lease joins the group as **one member** (other consumers outside the platform may share the group). Per partition, messages wait in a queue per key: a key's next message starts only when the one before has **settled**; messages without a key don't wait for each other. A run that fails or is cancelled is retried after the backoff (a new run, attempt n + 1, the same delivery record); after `maxAttempts` the message is produced to `deadLetterTopic` (its key, value and headers, plus `ow-error`, `ow-workflow`, `ow-run-id`, `ow-source-topic`, `ow-source-partition`, `ow-source-offset`, `ow-attempts`) and settles as `dead_lettered`, or, without one, settles as `dropped` (logged, counted). Offsets are committed up to the lowest unsettled message of each partition, every 5 s and when partitions are revoked or the lease is lost; partitions are paused while `maxInFlight` and the waiting messages are full. After a takeover, messages past the committed offset come again and the shared duplicate rules apply (a succeeded run: skipped; a running one: waited for). A run's input: `startTrigger.data` the value (JSON when it is JSON, else text; null for a tombstone), `startTrigger.message` `{topic, partition, offset, key, headers, timestamp, attempt, groupId}`. Run trigger type `kafka`.
- **Definition, projection, Git:** `triggers.sqs` and `triggers.kafka` in `packages/definition` (no schema version bump; names unique within each kind; the resource must be of the kind), migration `0034` (the kinds in the trigger kind and run trigger type checks, `queue_deliveries`), projected from the live release like Pub/Sub's, releasing needs Use on their resources, `@ow/collab` matches them by name, Git carries them in the definition. The query editors' `messages` fields merge as text in collab.
- **Web:** the SQS and Kafka resources' settings (the AWS identity fields shared with MSK IAM, the server's identity offered only where allowed and to admins; brokers, auth, TLS and certificates), badges, the send and produce query forms (workflow inspector, playground, app code panel), the triggers form's SQS and Kafka sections next to Pub/Sub's (one queue section component per kind) with each trigger's live line, the run page's message line, `startTrigger.message` typed per kind.
- **Ops:** log lines (`component: sqs` / `kafka`), runbooks `docs/runbooks/sqs.md` (a queue, its visibility timeout and redrive policy, the IAM actions: `sqs:ReceiveMessage`, `DeleteMessage`, `ChangeMessageVisibility`, `GetQueueAttributes`, `SendMessage`) and `docs/runbooks/kafka.md` (auth modes, ACLs: `READ` on the topics and the group, `WRITE` on the dead-letter topic, offsets, rebalances), `.env.example` (`AWS_SERVER_IDENTITY`), `docker-compose.aws.yml` (`~/.aws` mounted read-only, like the gcloud one) and an optional local Kafka (`docker-compose.kafka.yml`).
- **Tests:** a fake SQS endpoint and a fake STS in `@ow/connectors/testing` (queues standard and FIFO, visibility timeouts, receive counts, redrive to a dead-letter queue, long polling, a way to fail a call; it checks requests carry a SigV4 `Authorization` for the expected key); Kafka against a throwaway `apache/kafka` 4.x container, as MySQL's tests do (listeners for plaintext, SASL SCRAM over TLS and mTLS; skipped without Docker); the MSK IAM token checked against a fixed SigV4 signing; consumer tests per adapter; the done-when in Playwright through the fake SQS and the Kafka container.
- **Not in M26:** SNS (beyond what an SQS subscription delivers; SNS-wrapped bodies are passed through as they are), Kinesis, RabbitMQ and other brokers; Kafka exactly-once transactions; the Schema Registry (Avro, Protobuf: values are passed as JSON or text); SSH tunnels to Kafka; batching several messages into one run; SQS push via Lambda.
- **As built** (session 32, handoff §9u): as designed above, with these choices made while building: the adapter interface is `pull`, `extend`, `ack`, `fail` (answering `nacked`, `retried`, `dead_lettered` or `dropped`, given the run's error), `close`, `reset`, and a message's input may be a function of its attempt (Kafka's `startTrigger.message.attempt`); migration `0034` was written by hand (drizzle-kit asks interactively about a renamed table; the snapshot was derived and `generate` then finds nothing); the worker's log component is `queue`; Kafka's client is **Confluent's `@confluentinc/kafka-javascript`** (a spike against `apache/kafka:4.1.0`: `kafkajs` worked too but is unmaintained and warns on Node 24), its low-level `KafkaConsumer` polled by a **background loop** (a member that stops polling is dropped) with the KafkaJS-style admin and producer; librdkafka reports a wrong password or an untrusted certificate only as "Broker transport failure", so the client keeps librdkafka's logged errors and quotes the telling one; **a FIFO queue is received one message at a time** (a batch may carry several messages of one group, which would run at once); only admins set an SQS endpoint (it receives signed requests and the messages); MSK IAM tokens are presigned with `@smithy/signature-v4` and equal AWS's own signer's at the same moment; the produce query answers each partition's first offset (no per-message offsets in the send's answer); a dead letter that fails to send is sent again later without another run. Found while building: the Kafka client kept a disconnected producer after `close()`; M19's done-when read the triggers query's `pubsub` field, now `queue`. The done-when ran in Playwright through a fake AWS (STS and SQS, signatures checked) and a Kafka container; real AWS and MSK are for the Compose check.

## 2.30 Built-in connectors (M27)

Every API today goes through a REST resource someone has set up with a base URL, its auth and its allowed hosts, and its queries are raw HTTP: posting to Slack means knowing `chat.postMessage`, reading a sheet means knowing the Sheets API's ranges and value arrays. M27 adds what Retool ships for that: a **built-in REST API resource** that needs no setup, and **five resource types** for services Optiply uses, each with forms for the common actions. They share one HTTP core taken out of the REST connector, so auth (including M9's OAuth), the private-network guard, redirects, size limits, retries on 401 and secret scrubbing behave the same everywhere.

- **Agreed with the user at the start of M27 (session 33, 2026-10-30):** the built-in REST resource works in **workflows, apps and the playground** (any public URL, private addresses refused, auth typed per request, like Retool's `restapi`), not workflows only and not behind an admin's host list; Slack, HubSpot, SendGrid and Google Sheets are **their own connectors with action forms** plus a raw API call (not REST presets, and not every endpoint: the common actions); GraphQL is **schema-aware** (introspection, completions and checks in Monaco). Worked in away mode, as M25 and M26.
- **The HTTP core** (`packages/connectors/src/http-core.ts`): what `rest.ts` does after a request is built, made a function of a request and a small policy: auth applied (`none`, `apiKey`, `bearer`, `basic`, `oauth2ClientCredentials`, `oauth2AuthorizationCode` through `CredentialSource`, `custom` flows), a fresh token and one retry on 401, hosts checked against the policy (a base host plus `allowedHosts`, or **any public host** for the built-in resource), private addresses refused unless allowed or tunnelled (M17), redirects followed only to allowed hosts, the response limit, bodies read as JSON or text or base64, secrets scrubbed. REST keeps its behaviour and its tests, now on the core. A connector may declare **`authorizationCode(config)`**, which M9's connect routes and token store ask for instead of reading REST's `auth` field, so any type can sign in through OAuth (one connected account per environment, or per person, as REST).
- **The built-in REST API resource** (type `restapi`, slug `rest_api`, `systemKind: 'rest'`): made at startup like the Database resource (a user's own `rest_api` blocks it with a clear message), with an empty config in every environment (new environments get one); **Use for All Users** when it is made, then grants like any resource's; its settings can't be changed (M7's built-in rule). Its query is REST's (`method`, an absolute `url`, `params`, `headers`, `body` with JSON, form, raw and multipart) plus a per-request **`auth`**: `none`, `bearer` (`token`), `basic` (`username`, `password`) or `apiKey` (`in`, `name`, `value`), every value a template: a workflow takes a secret config var (`{{ configVars.STRIPE_KEY }}`), scrubbed as config var secrets are. Any public http(s) host, private addresses always refused (no setting, no SSH), redirects re-checked, 10 MB. **When the values come from an app's viewer** (`untrustedValues`), the scheme and host must be literal in the query text and the viewer's values fill only path segments (one encoded segment each, as REST), query parameters, headers and the body, so a viewer can't aim it at another host. Definitions just name `rest_api`, so a workflow using it deploys from Git to any instance.
- **GraphQL** (type `graphql`): config REST's (an endpoint URL, headers, params, auth with M9's OAuth and custom flows, allowed hosts, private network, SSH), secrets REST's. Query `{query, variables, operationName?}`: the query text has **no `{{ }}`** (values go in variables, so nothing is pasted into GraphQL), `variables` is JSON with `{{ }}` (`renderJson`), headers per query as REST's. A response with `errors` is the query's error (`code: 'query'`, message and path from the first, all in `details`, partial `data` kept in metadata); HTTP errors as REST's. **Introspection**: `resources.graphqlSchema({resourceId, environmentId})` runs the standard introspection query through the resource (needs Use), cached per resource config version for 10 minutes; Test connection runs `{ __typename }` and reports the schema's type count. ## 2.33 More brokers (M30)

M26 split M19's Pub/Sub consumer into one shared consumer (a lease per trigger, a run per message, held while it runs, ack on success, the broker's own redelivery and dead-lettering on failure, duplicates recognised by message id) and an adapter per kind. M30 adds three kinds of broker on it, and the Kafka Schema Registry.

- **Planned in away mode (session 36, 2026-11-03, overnight)** after M29, in the order the user chose; defaults taken without the user are listed in "As built".
- **RabbitMQ** (type `rabbitmq`, `amqplib`, MIT): config `host`, `port` (5672, or 5671 with TLS), `vhost`, `username`, `tls`, an optional CA; secret `password`; the private-network guard as REST's (`allowPrivateNetwork`), SSH tunnels out of scope. Query `publish`: `exchange` (empty: the default exchange, so `routingKey` is a queue), `routingKey`, `messages` as M26's (JSON with `{{ }}`, one or an array of `{body, headers?, contentType?, messageId?, persistent? (default true), priority?, expiration?}`; a non-string body sent as JSON), published with **publisher confirms** so a query succeeds only when the broker has the messages. Test connection: the broker's product and version. **Trigger** `triggers.rabbitmq` `{resource, queue, environment}`: a consumer with a prefetch of the consumer's in-flight limit, deliveries buffered for `pull`; **ack on success; nack without requeue on failure**, so the queue's dead-letter exchange applies (or the message is dropped: the docs say to set one); held messages need no extension (unacked messages stay with the channel); a channel closed by the broker or a lost connection hands them back (the next worker gets them, marked redelivered). ## 2.39 JavaScript packages (session 46, before M36)

Workflows and apps can use npm packages in their JavaScript code, the way they use Python packages (M23, §2.26).
The user asked for it in session 46 (2026-11-12) and decided two things:

- **Bundle into the sandbox**, rather than run Node in nsjail like Python. This keeps one mechanism for workflows
  and apps, keeps `fetch` and workflow-function calls working, and keeps runs fast. The cost is that only packages
  that work without Node's built-ins can run.
- **One shared, scope-based list of registries**: M33's `npm_registries`, now **Settings → npm registries**
  (`/settings/npm`, with `/settings/components` redirecting there). There is no per-workflow index picker.

The plan is `~/.claude/plans/js-packages.md`.

- **The definition:**
  - Workflows have `settings.javascript.packages`. Apps have a top-level `javascript.packages`, which is refused on
    a module because a module's code uses its app's packages.
  - Each line is `name` or `name@range` (a semver range or a dist-tag), checked by `parseJsPackage`
    (`packages/definition/src/js-packages.ts`). URLs, `git:`, `github:`, `file:`, `link:`, `workspace:` and `npm:`
    aliases, paths, `user/repo` and names npm refuses are all refused.
  - The list holds at most 30 packages. A bad line is `invalid_js_package` on that line.
  - In Git it's `package.json` next to `workflow.json` and `app.json`: `{"private": true, "dependencies": {…}}` in
    the author's order. An empty range means a bare name. Only `dependencies` is read back.
- **Import lines** (`packages/expressions/src/imports.ts`):
  - JS code bodies (code blocks, loop runners, an app's JS queries, transformers and scripts) may start with
    `import` lines, after comments.
  - `parseImports` finds where each line ends with acorn's tokenizer, then parses each line on its own as a module,
    so the body doesn't have to be strict-mode code.
  - `rewriteImports` turns them into `const __owImportN = __owImport("x"), d = __owImportN.default, { "a": b } =
    __owImportN;` on the same line, keeping the line breaks after it, so error lines stay right.
  - Analysis (`freeIdentifierRefs`) reads the body with the imports blanked out, so other offsets don't move, and
    leaves the imported names out.
  - An import of a package that isn't listed, or of a file inside one (`zod/lib/x`), is `unknown_js_import` on the
    package's name. Workflows check this with `importProblems`, and apps do too, except on modules.
- **Bundles** (`apps/server/src/services/js-bundles.ts`):
  - **Install:** `installDependencies` from M25/M33 runs npm with no install scripts, the admins' registries and
    tokens in a temporary `.npmrc`, 120 s and 200 MB.
  - **Bundle:** esbuild builds one IIFE (browser platform, ES2022, minified) from a generated entry that sets
    `globalThis.__owModules`: one getter per package that `require`s it on first use. A package failing to load
    doesn't take the others with it.
  - **Node built-ins:** a built-in with no npm package of that name installed becomes a Proxy stub that throws
    "X needs Node's fs" when used, and the build lists it as a warning. `confineTo` keeps esbuild inside the build
    directory.
  - **Size:** `JS_BUNDLE_MAX_MB` (default 5).
  - **Cache:** bundles are kept in `js_bundles` (migration 0046), keyed by `input_hash`: SHA-256 of the sorted
    dependencies, every registry's scope and URL (not the token) and the starting lock. They're found again by
    `bundle_hash`.
  - **Failures** are recorded too and answer again for a minute (`retryFailedAfterMs`; Install now and Try again pass
    0). A failure never replaces another process's ready row for the same inputs (`setWhere state <> 'ready'`).
  - **Retention:** `deleteUnusedJsBundles` runs in the worker's retention job. It deletes rows unused for 30 days
    that no release names, and failures after a day.
  - **Ranges** starting with `.` are refused, because npm reads them as directories.
  - **Concurrency:** builds run in the process that asks, two at a time, and the same input building at the same
    moment shares one build.
- **Runs:**
  - The engine's `JsModulesProvider` is asked as the run starts (`shared()` plus prefetch, like Python's
    environment) when the definition declares packages and some code imports one (`importsJsPackages`). Code with import lines waits for it, logging "Waiting for
    the workflow's JavaScript packages to install…".
  - The server's provider (`services/js-modules.ts`, `dbJsModules`) gives a release run its `js_bundle_hash`,
    rebuilt from `js_lock` when the bundle is gone. A draft run gets the package list's bundle.
  - `IvmRuntime` compiles a bundle once per isolate (`RunOptions.modules {hash, js}`) and runs it in each
    evaluation's context before the code. Its time counts toward the code's limit.
  - The stdlib prelude's `__owImport` does the CommonJS interop: `default` is the module itself, and its
    properties are named imports. ES modules come back as they are.
  - A failure is a `js_packages` block failure with npm's log.
- **Releases:**
  - `workflow_releases` and `app_releases` get `js_lock` and `js_bundle_hash`.
  - Publish and Git deploy keep the package list's bundle, which is the one draft runs used. A failure refuses the
    publish with npm's reason.
  - A rollback keeps the release's bundle, or rebuilds it from its lock and stores the new hash.
  - A bundle rebuilt from a lock under another hash, say after an esbuild upgrade, is renamed in every release that
    named the old one (`renameReleaseBundle`). `releases.get` leaves `jsLock` out.
- **Apps:**
  - `apps.open` returns the live release's `jsBundleHash`. The editor's preview asks `jsPackages.install` (`retry: false`) for the
    draft's list, waiting until the list has been still for 800 ms and skipping lists with problems.
  - The page fetches `GET /api/js-bundles/<sha256>.js?app=<id>` (with `&branchDraft=<id>` for a Git branch draft
    in the editor). It's served only for an app the caller can see. A bundle one of that app's releases names goes
    to anyone with Use, rebuilt from the release's lock when it's gone. The bundle of the app's draft list (or the
    branch draft's) goes only to people with Edit. Workflows' bundles never leave the server. Anything else is a
    404, as for an app the caller can't see. The user chose this in session 46, because a bundle can hold private
    registries' packages; component bundles are still open to anyone signed in.
  - The page sends the bundle to the sandbox as a `packages` message, before `start` and again on changes. The
    Worker, which still can't make requests, runs it as a function body. `owImport` (app-runtime) uses the same
    interop as workflows, and `functionRunner` rewrites import lines.
  - A query that ran on load before its package was listed doesn't run again by itself.
- **The editor:**
  - Workflow settings and App settings have a JavaScript packages field (`components/js-packages.tsx`). It shows
    problems by line and, for people with Edit, the install state: not yet with **Install now**; installed with
    versions, size and Node warnings; or failed with npm's output and **Try again**.
  - The routes are `jsPackages.state` (a workflow's state, without building) and `jsPackages.install`, a mutation
    because it may run npm, so it's never a GET. **Install now** and **Try again** build again. The app editor's
    field and preview pass `retry: false`, which answers a failure from the last minute instead of building again.
  - Monaco needed no change: a body with `import` lines is a module to TypeScript.
- **Audit:** `js.bundle_built` for each new bundle, with `fromLock` when it was rebuilt from a release's lock.
- **Reviewed** after step 6 by a separate agent. Its findings were fixed in step 7, and handoff §14 lists them. The
  bundle route's access rule (above) came from the same review.
- **The runbook** is `docs/runbooks/js-packages.md`. The e2e tests are `apps/web/e2e/js-packages.spec.ts` and
  `js-packages-done-when.spec.ts`.
